03 / Adding a New Feature

Build one feature.
Follow every boundary.

Trace one Entry from its OpenAPI contract through a command, database transaction, integration event, subscriber, and companion query.

Source checked: 20 October 2026 · ExampleCatalog and ExampleApi · Local, offline React Flow diagrams

One sliceCreate and read the same Entry
One commitBusiness writes and the outbox row
Later deliveryQueue consumption uses its own transaction

A bounded context owns a business model. Command Query Responsibility Segregation (CQRS) separates state-changing commands from read-only queries.

An outbox stores committed events for later publication. An inbox records consumer processing to prevent repeated database work.

01 / Choose the slice

Start with one observable result

This guide follows one existing feature: create an active system Entry, read it, and process its integration event.

The sample Entry has group settings, key page-size, value 25, and no target identifier.

The public API calls this resource an example. Its PHP bounded context is ExampleCatalog, and its domain term is Entry.

Existing implementation. The linked classes and PHP excerpts already exist. Reconstruct their sequence when adding your own feature. Do not duplicate these endpoints.

Sample requests and JSON values are illustrative inputs. They do not create a new feature, table, event, or subscriber in this repository.

  1. Define the request, access policy, success response, and failure responses.
  2. Select the context that owns the business rules.
  3. Add the required contracts, behavior, adapters, and registration.
  4. Verify the full call path and its failure paths.
  5. Update contracts, request examples, documentation, and the changelog together.

The Entry HTTP boundary uses explicit mapping. The shared ObjectMapper is available when a typed input object needs Valinor mapping.

For that alternative, validate root shape and size first. Reject unknown fields and wrong scalar types. Translate mapping errors into safe input errors.

04 / Command and behavior

Keep the command synchronous and result-free

Create a command under Contracts/Command only for a state-changing use case. Implement Shared/CQRS/Command.

Keep only required use-case data. Validate business values before they can enter the handler.

Use typed immutable fields for new fixed inputs. Keep stable serialization when other code depends on toArray().

Current AddEntry constructor. The surrounding readonly class and imports are omitted.

public function __construct(
        string $entryId,
        EntryType $type,
        int|null $typeTargetId,
        string $group,
        bool $isActive,
        string $key,
        string $value,
        array|null $details = [],
    ) {
        $this->identity     = new EntryIdentity($type, $typeTargetId, $group, $key);
        $this->identifier   = EntryId::fromString($entryId);
        $this->active       = $isActive;
        $this->entryValue   = new EntryValue($value);
        $this->entryDetails = $details === null ? null : new EntryDetails($details);
    }

Create the handler under Application/CommandHandlers. Depend on context ports and application services.

Current AddEntryHandler::handle(). The injected services and imports are omitted.

public function handle(Command $command): void
    {
        $writes      = $this->writes;
        $transaction = $this->transaction;
        $work        = static fn () => $writes->add($command);
        $domainEvent = static fn (IntegrationEvent $event): EntryAdded => new EntryAdded($command, $event->occurredOn());
        $transaction->execute($work, $domainEvent);
    }

The handler delegates creation to EntryWrites. The transaction service wraps that work and its event publication.

Current EntryWrites::add(). The injected write port and clock are omitted.

public function add(AddEntry $command): EntryAdded
    {
        $clock        = $this->clock;
        $now          = $clock->now();
        $entryId      = $command->entryId();
        $type         = $command->type();
        $typeTargetId = $command->typeTargetId();
        $group        = $command->group();
        $isActive     = $command->isActive();
        $key          = $command->key();
        $value        = $command->value();
        $details      = $command->details();
        $entry        = Entry::create($entryId, $type, $typeTargetId, $group, $isActive, $key, $value, $details, $now);
        $repository   = $this->repository;
        $repository->add($entry);

        return new EntryAdded(new EntryAddedPayload($entryId, $type->value, $typeTargetId, $group, $isActive, $key, $value, $details), $now);
    }

Entry::create() owns aggregate creation. The repository owns persistence. Both receive the same explicit mutation instant through this flow.

A privileged use case must carry typed AccessControl. Its handler must enforce the named privilege before reads or effects.

AddEntry currently relies on the route’s API key and USER authentication. It does not declare a named application privilege.

Do not copy an unrelated privilege or infer ownership from typeTargetId. Define the required policy for the new behavior.

The buses only resolve and call handlers. They do not add validation, retries, authorization, asynchronous execution, or transactions.

See CQRS rules and Entry aggregate behavior.

06 / Transaction and events

Publish the business fact before commit

One create operation: business transactionDrag to move · Use + / − to zoom · Select a step

Loading the local diagram…

Read this flow as text
  1. NewExample constructs AddEntry. AddEntryHandler enters EntryEventTransaction, which calls IntegrationEventTransaction.
  2. EntryWrites reads Clock, creates Entry, and saves it. The write adapter flushes inside the active database transaction.
  3. EntryEventTransaction publishes the optional domain event. The event manager runs local integration subscribers and appends one outbox row.
  4. DoctrineIntegrationEventTransaction flushes and commits. The HTTP action can now return 204 and the identifier. Broker delivery remains pending.

EntryEventTransaction delegates to Shared/Persistence/IntegrationEventTransaction. Production DI binds it to DoctrineIntegrationEventTransaction.

Current production transaction wrapper. The injected entity manager and event manager are omitted.

public function execute(callable $transactionalWork): void
    {
        $eventManager  = $this->eventManager;
        $entityManager = $this->entityManager;
        $connection    = $entityManager->getConnection();
        try {
            $connection->transactional(static function () use ($transactionalWork, $eventManager, $entityManager): void {
                $event = $transactionalWork();
                $eventManager->dispatchEvent($event);
                $entityManager->flush();
            });
        } catch (Throwable $exception) {
            $entityManager->clear();

            throw $exception;
        }
    }

The callback returns one complete IntegrationEvent. Direct producer dispatch requires an active transaction.

The transaction, local subscriber repositories, and outbox adapter must share the same database connection.

A subscriber exception, outbox insert failure, or final flush failure propagates and rolls back database work. The wrapper clears the entity manager.

Delivery follows commit. A successful HTTP response means the business transaction completed. It does not prove broker delivery or subscriber completion elsewhere.

Keep domain and integration events distinct

Contracts/DomainEvents/EntryAdded is synchronous in-process notification. Its target attribute selects EntryAddedListener.

EntryEventTransaction publishes that domain event after the write and before integration dispatch. The current listener logs metadata.

Contracts/IntegrationEvents/EntryAdded is the versioned integration fact. The event manager runs local integration subscribers before the optional outbox insert.

Both DELIVER_VIA_QUEUE values run local subscribers. Only true adds an outbox row, including when no local subscriber exists.

Do not perform broker, HTTP, file, or process effects inside transactional work or business subscribers.

Current reference listeners emit debug logs. Those logs cannot roll back with database writes. They are not durable business effects.

Read this flow as text
  1. OutboxRelayService claims a committed pending row. OutboxPublication publishes through OutboxMessagePublisher and the selected transport.
  2. RabbitMQ or SQS delivers the event metadata and payload. ExternalIntegrationEventMessageProcessor validates metadata and replay-window eligibility.
  3. The processor opens processOnce for consumer name and message ID. The dispatcher resolves name plus version and maps EntryAddedMessage.

The consumer requires an immutable occurrence time within the previous seven days. Missing, malformed, future, or older times are permanent failures.

The outbox can retry beyond this window. Monitor pending age before otherwise valid events become ineligible for consumption.

dispatchExternalEvent() does not append the received event to the outbox. A consumer does not republish a message automatically.

Consumer database work must use the inbox connection. A processed duplicate acknowledges without repeated dispatch.

For provider effects, use the existing external-effect pattern. A provider call cannot join the inbox database transaction.

See inbox and external-effect rules before adding email, SMS, or another network effect.

The existing outbox:relay and queue:consume runtimes require configured transports and supervised workers.

Registering an event does not start those workers or establish deployed broker topology. Verify those facts on the authorized target.

11 / Failures and retries

Keep three idempotency boundaries separate

BoundaryCurrent behaviorRequired design check
HTTP replayA separate durable claim precedes the business operation. Response completion is another commit. Matching completed responses remain for 24 hours.Keep operation ID, caller, key, and exact fingerprinted request stable. A crash after commit can leave an unresolved claim.
Outbox publicationA 60-second claim protects relay work. Failed publication retries after 2–256 seconds, without a terminal attempt limit.Publishing can succeed before the row is marked published. Expect redelivery of the same message ID.
Consumer inboxIdentity is (consumer_name, message_id). Consumer database work and processed_at commit together.Duplicate delivery must not repeat committed database work. Do not claim exactly-once external effects.

Use the same HTTP key and unchanged request for a retry. Use a new key for a new intended operation.

A completed retry returns the original status, body, and selected headers, including Backendbase-Insert-Id.

Current authentication still runs first. A replacement token changes the request fingerprint. Revoked access cannot replay a protected response.

ConditionOutcome
Invalid JSON, field type, key, or valueReject at the boundary with HTTP 400. Keep business state unchanged.
Missing or invalid accessReject under the API policy. The protected write must not reach business work or replay.
Duplicate nonremoved Entry identityEntryAlreadyExists maps to HTTP 409. Keep the existing Entry unchanged.
Missing detail resourceResourceNotFound maps to HTTP 404.
Changed request with the same scoped replay keyHTTP 422, idempotency/request-mismatch.
Active or unresolved matching replay claimHTTP 409, idempotency/request-outstanding. Waiting does not release an unresolved claim.
Replay storage or encryption failureHTTP 503. Business work can already have committed before response storage fails.
Local subscriber or outbox failurePropagate the failure and roll back database writes. Unexpected HTTP failures map to safe Problem Details.
Invalid queue metadata, unknown version, missing subscriber, wrong interface, or mapping errorPermanent consumer failure: reject through the failure policy when identifiers are available.
Other consumer or infrastructure exceptionRoll back consumer work and retry. The failure policy makes the fifth recorded transient failure terminal.
Closed ORM session after consumer failureConsumerRestartRequired preserves the retry/reject outcome. The transport stops consumption for supervisor restart.

Already completed application errors can also replay. A stored 500 or 503 does not automatically execute again.

Before retrying after an uncertain result, retain the original key and inspect business and messaging evidence.

Unresolved HTTP claims have no automatic expiry or takeover. After completed-response expiry, the same key can execute again.

Do not delete claims or reset evidence to force execution. Follow HTTP recovery rules.

Return application/problem+json with root Problem Details and a matching integer status. Do not expose traces or credentials.

Add a new domain problem only for a new expected failure. Align its stable code, HTTP mapping, OpenAPI, translations, and tests.

Log safe correlation fields. Do not log request bodies, replay keys, credentials, or full event payloads.

Synchronize the complete feature

  1. Update affected OpenAPI sources and regenerate the merged document.
  2. Update the Bruno write request and the companion read request.
  3. Align headers, input values, statuses, response fields, and replay assertions.
  4. Check affected material in resources/platform, resources/docs, and resources/skills.
  5. Update context instructions when ownership, invariants, or verification entry points change.
  6. Add the related CHANGELOG.md entry under Unreleased.
  7. Review the final diff for unrelated changes and generated artifacts.
  8. Report executed checks, concrete failures, and unverified targets.

For a documentation-only change, check meaning, links, code examples, script syntax, and browser rendering. PHP analysis and application suites are not required.
