01 / IdentityAndAccess

Configure registration.
Control identity access.

Find every identity setting, understand its effect, and change it at the correct boundary. Start with required fields and verification proofs.

Source checked: 20 October 2026 · Applies to UserApi, ExampleApi, and SystemAdminApi · Local, offline React Flow diagrams

25 settingsEvery leaf in identity-global.php
4 proof modesMobile, email, both, or neither
2 realmsSeparate USER and ADMIN trust

An Account owns email, mobile, password credentials, and optional names. An actor grants User or SystemAdmin access to that Account.

A realm defines a separate authentication area. UserApi and ExampleApi share the USER realm. SystemAdminApi uses ADMIN.

Required input and required proof are separate. Email and mobile input are always required. Deployment settings select which contacts require proof before registration.

Read the registration flow as text
  1. Validate email, mobile, password, optional names, and any supplied context token.
  2. Require a context token when either proof is required.
  3. Acquire email and mobile slots in that order when a context is supplied.
  4. Read server time after acquiring the slots.
  5. Validate each required proof against the contact, realm, purpose, and freshness window.
  6. Select fresh, matching, unused optional proofs when available.
  7. Create the Account and User, store credentials, and consume selected proofs in one transaction.
  8. Persist registration acceptance and the ownership result.

What changes for existing Accounts?

Successful registration stores registrationAccepted: true. Registration stores ownershipVerified: true only when it consumes evidence.

USER login checks stored registration acceptance. It does not reapply the current proof policy. Existing accepted Accounts and sessions remain eligible after a policy change.

Legacy Account state without registrationAccepted derives acceptance from validated ownership. Reads do not rewrite the record.

Missing, expired, unconfirmed, future, consumed, or mismatched optional evidence does not block registration. Required evidence must pass every check.

These switches do not disable verification endpoints, select notification providers, or change Admin ownership and approval rules. There is no policy discovery endpoint. Clients must use the deployment policy.

03 / Ownership and loading

Where are settings managed?

Deployment environment variables supply values. PHP configuration providers define their structure and defaults. Typed settings validate values before their consumers use them.

The application has no settings management API or Admin screen. Edit the deployment environment, secret injection, or the relevant PHP provider.

An empty environment string is present. It does not activate a default. Numeric variables use strict parsers. Malformed numeric text stops configuration loading.

There is no single eager configuration schema. Validation can occur when a lazy dependency or settings method is first used. A passing liveness request does not prove identity configuration is valid.

The public bootstrap reloads runtime configuration on each request. Long-running processes retain constructed dependencies and require restart after changes.

Live credential values are not persisted in container caches. Route, Doctrine, and mapping metadata can be cached. Clear relevant caches after changing those sources.

Common key and realm validation

  • Key identifiers contain 1–64 ASCII letters, digits, periods, underscores, or hyphens.
  • Required settings strings contain 1–255 bytes without spaces, ASCII control characters, or DEL.
  • An active key is required. Omit both previous fields when no previous key is needed.
  • Both realm policies are validated when a realm policy is requested.
  • USER and ADMIN issuers and audiences must differ. Their active and previous decoded signing key sets must not overlap.
  • Signing uses HS256. There is no algorithm setting. Keep proof and HTTP replay keys separate from signing keys.

Requesting an existing context slot returns its current state without another notification. A contact change requires a new context.

Explicit resend replaces the code and invalidates the previous generation. It preserves failed attempts. Verified or consumed evidence cannot be renewed through resend.

Repeated successful confirmation preserves the original verification time within its recovery window. A new registration attempt with consumed required evidence conflicts.

After a lost registration response, first retry the original HTTP operation with its unchanged request and key. Normal login can recover access after confirmed registration.

Verify a stored email after User login

Use POST /identity/contact-verifications with contactType: email and a new context token. Supply the USER bearer token.

This evidence uses the Account-bound user-contact-verification purpose. It cannot authorize registration or change the stored email.

Confirmation preserves ownership, passwords, authentication versions, and sessions. The response has registrationValidUntil: null.

Renew automatically in browsers and mobile apps

An expired access token does not end a live session. The client exchanges its refresh credential for new tokens.

The server cannot renew a token on a device by itself. Import the session client helper into the browser or mobile application.

The helper uses one renewal promise per client and a shared host lock across API surfaces. Web Locks coordinate browser tabs.

Native clients share an in-memory host queue. Keep one shared helper module and secure storage adapter in the app.

Use one client instance per API base URL. UserApi and ExampleApi on the same host share the renewal lock.

Rotation, retries, and concurrent requests

Each refresh token contains canonical Account and session identifiers plus a 32-byte random secret. Redis stores only its SHA-256 hash.

Rotation preserves earlier access-token records until their fixed expiry. This permits requests that were already in progress.

A known consumed refresh token used for a new operation revokes the session. Unknown secrets and wrong realms cannot revoke another session.

Consumed-token hash markers expire at the original maximum deadline. Refresh authentication runs before response replay and checks current database eligibility.

A matching retry returns the same token pair or cookie. Replay responses remain encrypted, including the Set-Cookie header.

A later rotation can replace the replayed result. The response guard returns 409 with identity/conflict before sending an obsolete cookie.

The helper then tries one new renewal with its current credential. Other conflicts and dependency failures retain the pending operation for inspection or retry.

Uncertain network, response, or secure storage failures retain the renewal key and body in memory. A process restart loses that pending operation.

If a mobile process stops before saving a rotated token, the next login can be required. Do not retry a consumed token with a new key.

Writes through identity.request() require an explicit Idempotency-Key. The helper retries one authentication failure with the unchanged key and body.

The helper does not repeat an application write after an uncertain network failure. Reuse its original key when the caller retries.

Legacy sessions retain their original expiry and cannot renew. They receive the new behavior after the next password login.

Rolling back to a server without version 2 sessions requires controlled logout. Follow the session recovery procedure.

Sources: SessionPolicy, atomic renewal scripts, and refresh authentication. Basis: OAuth security best practice for refresh rotation and OWASP browser storage guidance. The endpoint is a first-party session API.

How is Admin access managed?

Admin access is persisted authorization state. It is not a deployment flag. Public Admin registration is absent.

After bootstrap, an authenticated Admin invites an eligible Account and supplies invitation evidence. A separate approval operation supplies different approval evidence.

An Admin cannot approve its own enrollment. Optional Admin contact verification grants neither approval nor a session.

No-proof registration does not grant Admin eligibility. Such an Account can have registration acceptance without verified ownership. Later USER email confirmation preserves ownership. The current API provides no general ownership elevation operation.

For the first Admin, use a User registration that consumes fresh proof. Then use the local operator invitation and approval procedure.

Preview examples. Replace the identifiers and evidence references for the authorized target.

bin/backendbase identity:operator \
    --action=invite-first-admin \
    --target-id='<account-uuid>' \
    --operator='<operator-reference>' \
    --invitation='<invitation-evidence>'

bin/backendbase identity:operator \
    --action=approve-first-admin \
    --target-id='<returned-admin-actor-uuid>' \
    --operator='<operator-reference>' \
    --approval='<separate-approval-evidence>'

Preview is the default. Application requires an authorized local root process and --apply. The first invitation requires no existing Admin row, including removed rows.

Operator approval permits only the sole pending active Admin. Operator setup and manual seeding share a database-scoped lock with a five-second acquisition wait.

database:seed-admin is a separate manual bootstrap for the fixed, approved initial identity. It is not a general Account promotion tool.

That seeder requires a private password file and local root authority for application. It does not create a User, send notifications, or issue tokens.

Procedures: identity operator and session recovery. Authentication rules: security guidance.

Required request headers

Send X-Source-Id: user, example, or system-admin for the selected API. Send Content-Type: application/json for JSON request bodies.

Every POST, PUT, PATCH, and DELETE requires Idempotency-Key. Protected writes require current bearer authentication. Refresh requires its current refresh credential. ExampleApi additionally requires its API key.

GET, HEAD, and OPTIONS do not require an idempotency key. Health and preflight routes require no credentials. Cross-Origin Resource Sharing (CORS) does not grant identity authority.

Retry behavior is part of the contract

Generate a new unpredictable key for each intended operation. Keep the same key and unchanged request for a retry.

Unchanged means the same method, path, query, exact body bytes, credentials, and representation headers. JSON whitespace can change the fingerprint.

Completed responses remain replayable for 24 hours. Replay does not execute another renewal. Protected authentication can extend idle. Proof deadlines and quotas remain unchanged.

A login retry returns the original token. A new login requires a new key. An unresolved claim remains blocked without automatic takeover.

Contact cooldowns and HTTP replay are separate. A replayed 429 response remains the original response. Inspect the outcome before starting a new intended attempt.

Identity request objects have a fixed 65,536-byte limit and a JSON decoding depth of 64. Unknown fields and type coercion are rejected.

Sources: RedisSettings, SessionRedis, RequestObjectInput, and HTTP idempotency. Related guide: HTTP retry and recovery examples.
