02 / HTTP idempotency

Keep one key.
Retry the same operation.

Idempotency lets a matching retry return a stored HTTP response without executing the operation again. Keep the key and request together.

Source checked: 20 October 2026 · Applies to UserApi, ExampleApi, and SystemAdminApi · Local, offline React Flow diagrams

1 keyFor one intended operation and its retries
24 hoursRetention after response completion
No takeoverUnresolved claims remain blocked

A claim is a stored record that reserves an operation key. A replay returns its completed response.

A timeout does not prove failure. Keep the original key. A new key can execute another operation.

01 / Client contract

Send a key with every write

Current write routes require Idempotency-Key. This includes login, registration, contact verification, session changes, administration, and Example writes.

HTTP methodKey requirement
POST, PATCH, DELETERequired on current write routes.
PUTSupported by the same middleware when a named write route is added.
GET, HEAD, OPTIONSNo key requirement and no replay storage.
  1. Generate an unpredictable key when an intended operation starts.
  2. Keep the key and exact request until the outcome is known.
  3. Reuse that key for retries of the same operation.
  4. Use a new key for each new intended operation.

Use the accepted header format

Send exactly one unquoted value with 1–255 ASCII characters. Start with a letter or digit.

Remaining characters can be letters, digits, periods, underscores, colons, or hyphens. Spaces, commas, quotation marks, and repeated values are rejected.

Idempotency-Key: 019f6322-1234-7000-8000-000000000001

A universally unique identifier (UUID) is suitable. UUID format is not required by the validator.

X-Request-Id identifies an HTTP attempt for diagnostics. It is separate from the operation key and can change between attempts.

Sources: ReplayInput, Idempotency, and shared OpenAPI components.

02 / Working request

Retry a UserApi login unchanged

This shell example uses the local UserApi base URL from the maintained Bruno environment. Use an existing, eligible test Account.

Replace the sample credentials before the first send. Generate a fresh key for that login operation.

The command uses POST /auth/login, operation ID userPasswordLogin, and the required X-Source-Id: user header.

userApiBaseUrl='http://127.0.0.1:8080/user-api'
idempotencyKey='019f6322-1234-7000-8000-000000000001'
loginBody='{"identifier":"ada@example.com","password":"valid-password-123"}'

sendLogin() {
    curl --silent --show-error --include \
        --connect-timeout 5 --max-time 15 \
        --request POST "$userApiBaseUrl/auth/login" \
        --header 'X-Source-Id: user' \
        --header 'Content-Type: application/json' \
        --header 'Accept: application/json' \
        --header "Idempotency-Key: $idempotencyKey" \
        --data-binary "$loginBody"
}

# First attempt.
sendLogin

# Matching retry. Keep the key, credentials, headers, and body unchanged.
sendLogin

An eligible login returns 200 with the session response key. A completed matching retry returns the original body and token.

The retry does not create another session or renew token expiry. The original token can already be expired or revoked.

Session renewal authenticates its refresh credential before replay. It rejects obsolete results before sending an earlier cookie. See automatic session renewal.

Both calls use the same serialized body. Rebuilding equivalent JSON can change whitespace or field order and cause a mismatch.

Bruno sends new keys by default. Maintained write requests use {{$randomUUID}}. Replace it with one fixed key when testing retries.

Registration retries return the original created identity. Contact request and resend retries do not send another notification after response completion.

An explicit contact resend is a separate operation with a new key. Retrying confirmation does not renew its stored verification time.

Compare login.yaml, Authentication/ModuleConfig.php, Bruno local environment, AuthenticationReplayTest, and ContactReplayTest.

03 / Request identity

Keep the scope and request content stable

The key scope contains the named route's operation ID, caller identity, and key. It does not use the key alone.

Authenticated caller identity contains the realm, Account ID, and actor ID. Public authentication operations use an anonymous caller scope.

Operation IDs separate the three inbound APIs. Keep those IDs stable while claims exist. A route name change creates a different scope.

A fingerprint is a keyed digest used to compare request content within that scope.

InputRetry requirement
Method, path, raw query stringKeep each value unchanged. Query parameter order matters.
Raw body bytesKeep exact bytes. JSON whitespace and field order matter.
Content-Type, Accept, Accept-Language, The-Timezone-IANAKeep the header values unchanged, including omission.
Authorization, Backendbase-Api-KeyKeep credentials unchanged. A replacement bearer token changes the fingerprint.
X-Request-IdNot fingerprinted. It can identify each attempt separately.

Different actors can use the same key independently. Different public callers with the same operation and key share one scope.

Different content under that public scope returns 422. It cannot return the first caller's stored result without matching the fingerprint.

The path belongs to the fingerprint. Reusing a key for another resource path under one operation ID causes a mismatch.

Sources: ReplayInput::identity() and MiddlewareReplayTest.

04 / Server behavior

Separate the claim from the application transaction

First accepted writeDrag to move · Use + / − to zoom · Select a step

The interactive diagram loads here. Read the flow steps below if it is unavailable.

Read the first-write flow as text
  1. Run applicable authentication, validate the key, and enforce the 65,536-byte raw body limit.
  2. Commit a unique claim before executing the application operation.
  3. Execute the operation with its existing application transactions and external effects.
  4. Encrypt and store the response before returning it to the client.

The shared middleware does not wrap the application operation in a database transaction. Claim storage and response completion are separate commits.

A crash after an effect but before response completion leaves an unresolved claim. A matching retry returns 409.

Completed matching retryDrag to move · Use + / − to zoom · Select a step

The interactive diagram loads here. Read the flow steps below if it is unavailable.

Read the completed-retry flow as text
  1. Run current authentication on protected routes before replay.
  2. Find the claim using the operation ID, caller identity, and key.
  3. Compare the fingerprint and decrypt the completed response.
  4. Return the stored status, body, and selected headers without executing the operation.

What does replay preserve?

Replay preserves the status and body. Stored headers are Content-Type, Cache-Control, Content-Language, Backendbase-Insert-Id, Location, Retry-After, and Set-Cookie.

Set-Cookie is encrypted with the response. Trace, transport, and cross-origin headers are not stored for replay. Outer middleware can add current response headers.

Returned errors and exceptions mapped by the HTTP error handler are stored after execution starts. This includes application 400, 429, 500, and 503 responses.

Errors before the claim are not stored. These include missing-key, current authentication, and raw body-size rejection.

Protected replay still requires current access. Retrying successful logout or token revocation with the revoked token returns 401.

Sources: Idempotency, ReplayExecution, ReplayResponse, and protected route order.

05 / Failure handling

Select the next action from the response

ConditionResponseClient action
Missing, repeated, malformed, or oversized key400 before executionCorrect the header before submission.
Completed matching requestOriginal status, body, and selected headersUse the original result. The response can be an error.
Different content under the same scoped key422, idempotency/request-mismatchRestore the original request for a retry. Review its outcome before starting a corrected operation.
Active or unresolved matching claim409, idempotency/request-outstandingKeep the same key. Use bounded backoff for an active attempt. Investigate a persistent unresolved result.
Claim, encryption, response storage, or decryption failure503Keep the original key. The operation can have completed before response storage failed.
Expired, revoked, or invalid protected credentials401 before replayFollow the authentication procedure. Do not infer that the earlier operation failed.
Connection timeout or lost responseNo reliable resultRetry the unchanged request with its original key within the retention window.

Read the Problem Details code and detail fields. Other business conditions can also return 409.

The middleware does not implement a client retry schedule. Select a bounded retry count and backoff for the client.

Waiting does not release an unresolved claim. A stored application 429 or 503 remains the original response on matching retries.

Failure evidence: ReplayFailureTest covers concurrency, stored errors, unavailable storage, and failure after an effect.

06 / Deployment settings

Configure one dedicated replay secret

Setting or limitCurrent contractSource
BACKENDBASE_IDEMPOTENCY_KEYBase64-encoded 32-byte secret. Maps to idempotency.key. Missing environment value defaults to empty text and fails validation.idempotency-global.php, ReplaySettings
Completed-response retentionFixed at 24 hours after completion. No retention configuration key.DoctrineRequestReplayStore
Raw request bodyMaximum 65,536 bytes before a claim.RequestObjectInput
Stored response bodyMaximum 1,048,576 bytes (1 MiB). Oversized or unserializable responses return 503 and leave an unresolved claim.ReplayResponse
Storage and encryptionRequestReplayStore uses Doctrine. RequestReplayCipher uses Sodium.dependency bindings

Generate a secret locally with PHP:

php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'

Supply that value through deployment secrets or local .env. Use the same value on every API instance sharing replay records.

Keep it separate from signing and contact proof keys. The public value in .env.example is for local development only.

The request key is not this secret. Clients send operation keys; the server uses its secret for fingerprints and encrypted responses.

The store uses http_request_replay. Request keys, raw bodies, and credentials are not stored as plaintext replay fields.

Responses, including tokens and personal data, are encrypted. Claims store digests and timestamps outside the encrypted response.

No online key rotation is implemented. Changing the secret invalidates retained fingerprints and encrypted responses. Follow the controlled rollout and recovery procedure.

Deploy the reviewed schema and secret before activating write replay. Stop writes during mixed-version activation and clear route caches.

See configuration and rollout for migration and replacement requirements.

07 / Operation lifetime

Keep uncertain outcomes blocked

StateMatching retryLifetime
No claimClaim and execute once.No stored protection yet.
Claim without a responseReturn 409.No automatic expiry or takeover.
Completed claimReturn the stored response.24 hours from completion. Reads do not renew expiry.
Expired completed claimRemove that record and permit another execution.Protection has ended, even if scheduled cleanup has not run.

Do not retry an uncertain operation automatically after its retention window. The same key can then execute another operation.

Remove expired completed responses

Run this command only on an identified, authorized target:

bin/backendbase idempotency:cleanup

Each run deletes up to 500 expired completed responses. It preserves unresolved claims. No schedule is installed automatically.

Investigate an unresolved claim

  1. Keep the client key and original request.
  2. Inspect business records, outbox records, Redis state, and provider evidence for the original outcome.
  3. Use separately authorized recovery only after proving the outcome of the exact claim.

There is no automatic reconciliation or claim-release command in this implementation. Do not delete claims or reset timestamps to permit retries.

External delivery can remain uncertain after a provider timeout. HTTP replay does not guarantee exactly-once external delivery.

Restore replay evidence consistently with business data. Lost claims or older restored claims can permit duplicate operations.

Sources: CleanupRequestReplays, DoctrineRequestReplayStore, and recovery procedure.
