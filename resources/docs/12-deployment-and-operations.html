01 · Overview

A release changes code, contracts, cache, and schema

Deployment is not only a source update. It must keep runtime configuration, generated OpenAPI, container cache, route cache, Doctrine cache, database migrations, and background consumers compatible.

Production boundary: Execute deployment scripts only with explicit release authority and verified backups.

02 · Preflight

Prove the release before it reaches a server

  • Run focused and full tests for the change.
  • Run PHPStan, cyclomatic complexity, and PHPCS.
  • Verify the Composer SBOM and package-content manifest.
  • Generate and validate OpenAPI.
  • Review every migration and its reverse operation.
  • Confirm required environment variables and secrets exist.
  • Confirm the target branch, release identifier, maintenance window, and rollback owner.
  • Confirm queue consumers remain compatible with existing messages.

05 · Database

Migration review is a release gate

  • Back up or confirm recoverable database state before a risky migration.
  • Verify the migration metadata table.
  • Run only reviewed migrations.
  • Watch locks and execution time for table changes.
  • Confirm application compatibility during rolling deployment.
  • Verify the schema and key queries after migration.
MySQL boundary: DDL can commit independently. Deployment records the dry-run SQL and migration output. A required hook confirms backup recovery before execution.

06 · Cache

Clear generated data when its source changes

bin/backendbase clear-cache removes files under the new release var/cache. A successful clear returns exit code zero. Strict deployment stops on a cache failure.

  • Clear merged configuration after environment or configuration changes.
  • Clear route cache after route changes.
  • Clear container compilation after dependency changes.
  • Clear Doctrine metadata after mapping changes.

08 · Health checks

Verify the request path and background state

  1. Request GET /_status for a cheap application liveness check.
  2. Request GET /_status/ready for dependency readiness.
  3. Confirm that readiness returns 200 and status: ready.
  4. Run outbox status.
  5. Confirm worker processes are running.
  6. Inspect new error and critical logs.
/_status/ready checks MySQL, Redis, the selected queue, and the object store. Each connection uses BACKENDBASE_READINESS_TIMEOUT_SECONDS. A failed check returns 503 with safe status data.

09 · Recovery

Prepare recovery before migration

  • Keep the previous release directory available.
  • Record whether the previous application supports the target schema.
  • Prefer a forward repair when MySQL has committed part of a schema change.
  • Use the required backup hook before migration.
  • Use rollback-release.sh only for the recorded previous revision.
  • Preserve recovery files, failed messages, and logs for diagnosis.

10 · Secrets

Inject target values outside source control

Each release links to a protected environment file under /opt/backendbase/shared. Protect database credentials, JWT signing keys, API keys, RabbitMQ credentials, AWS credentials, object-store credentials, and Tolgee keys.

Do not print or archive environment files in deployment output.

11 · Current risks

Known operational limits

  • The repository does not define the server-specific backup and process activation hooks.
  • The first conversion from a working tree to the release-link layout requires a maintenance window.
  • MySQL DDL needs backup recovery or a reviewed forward repair after partial execution.
  • No worker supervisor, scheduler definition, container deployment manifest, or alert configuration exists in the repository.

12 · Checklist

Release completion criteria

  • The deployed revision is known.
  • Dependencies install without development packages.
  • OpenAPI generates and validates.
  • Reviewed migrations complete.
  • Caches rebuild.
  • Health and outbox status are healthy.
  • Workers run the compatible revision.
  • Logs contain no new unexpected failures.
  • The rollback decision window and owner remain active.
