Overview

An inbound API is an HTTP adapter under src/Backendbase/Infrastructure/Inbound/{ApiName}. It owns transport concerns. It does not own domain rules or persistence.

Select

Choose the API

The shared bootstrap uses X-Source-Id to select the use-case directory and configuration slug for both public entry points.

Translate

Adapt HTTP input

Routes and actions turn headers, paths, queries, and JSON into commands or queries.

Return

Shape HTTP output

Actions convert read models and domain errors into HTTP status codes, JSON, headers, or empty responses.

Successful bodies use descriptive keys such as user, admin, and challenge. Do not add generic data wrappers or statusCode. ActionPayload serializes the supplied named body directly. Existing direct projections, health bodies, and empty responses keep their documented shapes. Problem Details errors retain status equal to the HTTP response status. Slim exception titles use standard HTTP reason phrases. Domain errors retain their mapped problem titles.

Current reference The repository contains ExampleApi, UserApi, and SystemAdminApi. Each API owns its controllers and route registration.

All 38 write operations require Idempotency-Key. Group authentication runs before replay. Claims preserve existing application transaction boundaries. See HTTP idempotency for the complete contract and recovery procedure.

UserApi/Controllers and SystemAdminApi/Controllers follow the same module pattern. Their module names match the OpenAPI tags: Authentication, Identity, and System. SystemAdminApi also has Administration.

Controllers/
├── ModuleRoutes.php                  # Explicit module registry
├── Root/Preflight.php                # Browser OPTIONS handler
└── {OpenApiTag}/
    ├── ModuleConfig.php              # ModuleRoute implementation and route prefix
    ├── AdministrationHttpInput.php   # Administration module only
    └── Handlers/                     # One action per documented operation

routes.php creates one group per registered module. Each route name matches its OpenAPI operation ID. Administration controllers and input belong to the Administration module.

Use fluent route declarations in ModuleConfig, following ExampleApi. Chain the HTTP method, setName(), and endpoint-specific add() calls. Use group() to apply common middleware once.

Authentication, Identity, and Administration modules define their realm once per group through RealmPolicy. RoutePolicy supplies only the endpoint action. ContactRoutePolicy supplies only contact settings. Neither policy sets or replaces the group realm.

Protected Identity and Administration routes share an empty-prefix subgroup. Add RealmAuthentication, then the fixed RealmPolicy. Slim executes the last added middleware first, so the realm policy runs before authentication. Keep action and contact policies on individual routes. Use non-static group callbacks because Slim binds them to the dependency container.

Public Authentication groups apply RealmPolicy and write replay through Idempotency and do not require a bearer token.

Anonymous authentication, health, and preflight routes remain outside protected groups.

Both APIs use the same IdentityAndAccess application operations. Reusable HTTP input, dispatch, and policy helpers belong under Infrastructure/Adapters/Http/Identity.

API key

API protection

ValidateApiKey checks the API key. Protected Example and Identity groups also validate USER bearer tokens. Example commands retain their business input.

The shared bootstrap also adds body parsing, routing, error middleware, a shutdown handler, and the response emitter.

API-key validation is active ExampleApi/middleware.php adds ValidateApiKey::class. It validates Backendbase-Api-Key on non-public paths and returns status 401 for a missing or invalid key.

Example operations require Backendbase-Api-Key. All except getExampleByCriteria also require Authorization: Bearer with a valid USER token. Missing or invalid credentials return 401. Unavailable authentication state returns 503.

ExampleApi exposes the same contact verification, registration, login, current identity, token revocation, logout, and Account closure operations as UserApi. Both APIs share USER signing settings and session state. Authentication routes require the API key without a bearer token.

Controller pattern

Business handlers extend Backendbase\Infrastructure\Adapters\Http\Actions\Action. The transport-only Liveness handler is directly invokable. The base class stores the PSR-7 request, response, and route arguments before it calls action().

final class EntryAction extends Action
{
    public function __construct(
        private readonly QueryBus $queryBus,
        protected LoggerInterface $logger,
    ) {
        parent::__construct($logger);
    }

    protected function action(): Response
    {
        $type = ExampleRequestInput::type(
            $this->request->getAttribute('type-slug'),
        );
        $params = $this->request->getQueryParams();

        $result = $this->queryBus->handle(new EntryQuery($type));

        return new JsonResponse(['data' => $result], 200);
    }
}

Controller responsibilities

  • Read path, query, header, and parsed-body data.
  • Validate untrusted input without changing accepted values.
  • Invoke one application operation through a command, query, or write-result orchestrator.
  • Map a read model to the response schema.
  • Select the HTTP status and response headers.

Do not put here

  • SQL or Doctrine repository calls.
  • Aggregate state changes.
  • Outbox or queue publishing.
  • Reusable business decisions.
  • Database transaction control.

Current boundary validation

ExampleRequestInput validates the example type, integers, strings, objects, and booleans. Invalid data raises InvalidUserInput before bus dispatch.

  • typeSlug must map to an EntryType.
  • typeTargetId body values are null or positive integers. Query values also permit integer strings; omitted or empty query values select null.
  • pageSize and page default to 1000 and 1.
  • PATCH treats omitted and null lookupValue, details, and isActive fields as unchanged. Other supplied values must be a string, object, and boolean.
  • ExampleRequestBody reads bounded JSON objects. Supplied non-null details must be objects with non-integer top-level member names.
  • Groups allow 1–32 UTF-8 characters, keys allow 1–160, and values allow 0–2048. Accepted text remains unchanged.
  • Nested detail objects and arrays retain their shapes. List responses do not infer image URL fields.
Validate all new fields at the boundary The current helper covers only selected fields. Do not rely on PHP casts as complete request validation.

CQRS dispatch

Read

Query action

  1. Validate path and query data.
  2. Create a typed query contract.
  3. Call QueryBus::handle().
  4. Map the read model to response JSON.
  5. Return status 200.
Write

Command action

  1. Validate path and JSON data.
  2. Create the typed public resource identity.
  3. Create a typed command contract.
  4. Call CommandBus::handle().
  5. Return status 204.

ChangeExampleDetails and RemoveExample put EntryIdentity in one command. Their handlers resolve the aggregate through the write repository and own the resource-not-found decision.

Client-visible write results

Command handlers and the command bus return void. A write response can use either approach:

  • Identifier only: Generate the public identifier before a create command or reuse an existing resource's public identity. Send it in the command and return it after successful execution. NewExample returns Backendbase-Insert-Id with status 204.
  • Resource representation: Call one application orchestrator with validated, typed input. It executes the command, waits for commit, then reads through a query or read port. It returns a declared result for the HTTP action to map. This is a permitted design, not the current create-endpoint implementation.

Keep orchestration in the owning context's Application layer. Keep input and result contracts in Contracts. Preserve command and read authorization, including direct read-port calls. Keep authoritative write lookup and transaction control in the handler or its called application service.

For an immediate representation, verify that the read source observes the committed write. Define missing-result and read-failure behavior after commit. A failed read does not undo the write. Do not repeat the command to recover a response. Follow the CQRS result rules for consistency limits and verification.

Add an endpoint

  1. Define the OpenAPI path, operation, headers, security, input schema, response schema, and errors.
  2. Add or reuse a bounded-context command or query contract.
  3. Add domain behavior, ports, adapters, and handlers before the HTTP controller.
  4. Create an Action under the affected API module.
  5. Sanitize and validate all untrusted input before bus dispatch.
  6. Add the route to ModuleConfig.
  7. Use API-key protection by default.
  8. Add focused controller and routing tests.
  9. Regenerate the OpenAPI file.
  10. Add or update the Bruno request when end-to-end coverage is required.
  • Request names use camelCase.
  • URL path parameters use kebab-case conventions.
  • Response attributes use camelCase.
  • Success and error statuses match OpenAPI.
  • The controller does not access Doctrine.
  • Invalid input never reaches a bus.
  • Write handlers own the missing-resource decision.
  • All affected inbound APIs are updated.
