04 · Critical findings

Priority reflects dependency direction and change impact

Accepted CQRS decision: Command and query contracts identify one handler in the same bounded context through a positional CQRSHandler attribute. The contracts are not distributed as an independent package. This mapping is an internal metadata decision, not a boundary violation. Tests must protect it.
Resolved · 01

The Identity and Access application boundary is established

HTTP controllers and middleware now depend on the TokenIssuer and TokenValidator ports. Jwt only manages the token flow through an injected codec and AuthorizationStore.

The middleware puts a typed AccessControl object in the request. The controller moves this object into the command. The application handler checks the required privilege before a transaction or repository call. A new architecture test prevents HTTP entry points from depending on the concrete Jwt class again.

Evidence: TokenIssuer.php, TokenValidator.php, AuthorizationStore.php, config/dependencies/redis.php:46-64, ChangeExampleHandler.php:28-39, IdentityAndAccessPortBoundaryTest.php:18-34.

Implemented actionThe TokenIssuer, TokenValidator, and AuthorizationStore ports were added. Authorization moved to the application handler boundary.
Resolved · 02

The Domain and Shared core no longer carry transport or container details

DomainException stores only a message and safe context. DomainErrorProblemDetailsMapper owns the public HTTP contracts. DomainEvents uses a native array and SPL interfaces. Container-aware buses, publishers, and event managers are under Infrastructure/Adapters.

Evidence: Shared/Domain/Exception/DomainException.php, Infrastructure/Adapters/Http/DomainErrorProblemDetailsMapper.php, Shared/Domain/DomainEvents.php, Infrastructure/Adapters/DomainEvents/ContainerAwareDomainEventPublisher.php.

Implemented actionTransport mapping moved to the HTTP adapter. Framework-backed implementations moved to Infrastructure. Architecture tests now protect both boundaries.
Resolved · 03

HTTP orchestration and PATCH validation are complete

PATCH and DELETE action classes no longer manage a query → decision → command sequence. Each action dispatches one command. The application handler loads the active aggregate through the write port. It makes the missing-resource decision at that boundary.

ExampleRequestInput preserves omitted lookupValue, details, and isActive fields as null. It rejects supplied values unless they are a string, object, and boolean. Invalid types produce the stable 400 Problem Details response.

Evidence: ChangeExampleDetails.php, ExampleRequestInput.php, ExampleInputValidationTest.php, ChangeExampleHandler.php.

Implemented actionNullable PATCH validators now reject invalid supplied types. HTTP regression tests cover all three fields and confirm that the command bus is not called.
Resolved · 04

Messaging ports hide direction and vendor details

MessagePublisher and MessageConsumer separate the two queue directions. They exchange typed Message, MessageSubscription, and MessagePublicationResult objects.

Notify returns NotificationResult. Notification adapters no longer expose their vendor clients or raw vendor responses.

Evidence: MessagePublisher.php, MessageConsumer.php, Messaging/Message.php, Notify.php.

Implemented actionDirection-specific ports and project-owned value objects replaced the combined array-based queue contract. Vendor-client access was removed.
Resolved · 05

Application services own retry and relay policy

OutboxRelayService owns the relay loop and publication decisions. OutboxRetryPolicy owns the 60-second claim and exponential delay. QueueMessageFailureService owns permanent, transient, and five-attempt outcomes.

DoctrineOutboxMessageStore and DoctrineQueueMessageFailureStore only claim, record, mark, clear, and apply supplied status values.

Evidence: OutboxRelayService.php, QueueMessageFailureService.php, DoctrineOutboxMessageStore.php, DoctrineQueueMessageFailureStore.php.

Implemented actionPolicy moved to framework-free application services. Doctrine adapters now implement persistence mechanisms only.
Resolved · 06

Adapters provide equivalent behavior for the same port

ExampleRepositoryContract now runs unchanged against memory and Doctrine adapters. It covers empty results, projections, ordering, pagination, active identity uniqueness, soft removal, and replacement.

ExampleStore enforces the same active lookup identity rule as Doctrine. Doctrine translates its constraint exception into the context-safe ExampleAlreadyExists error.

The registered version-one external DTO now preserves the producer's nested command field. ProducerConsumerContractTest builds the real event and provider registration, then maps it through the real registry and dispatcher.

Evidence: ExampleRepositoryContract.php, Memory/ExampleStore.php, Doctrine/ExampleWriteRepository.php, NewExampleAddedMessage.php, ProducerConsumerContractTest.php.

Implemented actionBoth repository adapters pass one contract suite. The producer payload maps into the registered typed carrier through the real dispatcher.
Resolved · 07

Architecture tests protect general dependency and metadata rules

Separate tests reject Application → Infrastructure and framework imports in the Shared core. Direction-specific tests reject inbound → outbound and outbound → inbound adapter dependencies.

AttributeTargetBoundaryTest checks one positional target, same-context placement, the required handler interface, and production-container resolution for every CQRS and domain-listener attribute.

Evidence: ApplicationDependencyBoundaryTest.php, SharedCoreFrameworkBoundaryTest.php, InboundAdapterDependencyBoundaryTest.php, OutboundAdapterDependencyBoundaryTest.php, AttributeTargetBoundaryTest.php.

Implemented actionFive focused architecture test classes now protect the previously open dependency and attribute rules.

05 · Strengths

Preserve the existing effective boundaries

Context-owned repository ports

Application handlers depend on bounded context contracts instead of Doctrine.

Read/write separation

Separate ports contain read models and aggregate persistence behavior.

Object-relational mapping isolation

The domain aggregate has no Doctrine attributes. A separate object-relational mapping (ORM) record acts as a mapper.

Replaceable adapter goal

Doctrine and memory adapters implement the same project interfaces.

Transactional messaging

Outbox, inbox, and external-effect operations use project-owned ports and transaction boundaries.

Effective architecture controls

Abstract syntax tree (AST) tests detect core direction violations and the HTTP → concrete Jwt dependency.

Token application ports

HTTP entry points use project contracts instead of concrete JWT or Redis classes for token creation and validation.

Authorization at the handler boundary

Example write handlers check named privileges before transaction and repository operations.

Example evidence: AddNewExampleHandler.php:21-36, Doctrine/ExampleWriteRepository.php:13-34, TokenValidator.php, config/dependencies/redis.php:46-64.

06 · Remediation order

All assessed remediation steps are complete

  1. Completed — establish the Identity and Access boundary. Token and authorization ports were added. HTTP, JWT codec, and Redis store roles were separated. Authorization moved to the application handler boundary.
  2. Completed — make the Shared core pure. HTTP Problem Details mapping, the native event collection, and container-aware Infrastructure adapters now enforce the boundary.
  3. Completed — enforce one entry point for one use case. Controller orchestration was removed. PATCH fields are validated at the HTTP boundary.
  4. Completed — narrow the messaging ports. Publication and consumption are separate. Typed message, subscription, publication, and notification results replace raw port values.
  5. Completed — remove policy from adapters. Application services own retry, dead-letter, relay, claim-duration, and backoff decisions.
  6. Completed — test adapter parity. Memory and Doctrine pass one repository contract suite. The real dispatcher maps producer data into the registered consumer DTO.
  7. Completed — expand architecture tests. Separate tests cover Application, Shared core, both adapter directions, and attribute targets.
Success criterion: Application and domain code must not change when an HTTP, CLI, or queue adapter changes. Inbound adapters must not change when Doctrine, Redis, or the broker changes.
