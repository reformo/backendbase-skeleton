01 · Kısa hüküm

İyi bir temel var; bağımlılık yönü her sınırda korunmuyor

En doğru tanım: Proje, Ports and Adapters öğelerini kullanan modüler bir DDD/CQRS mimarisidir. Katı bir hexagonal mimari değildir.
Çözüm güncellemesi: Bulgu 01 kapatıldı. HTTP girişleri artık TokenIssuer ve TokenValidator portlarını kullanır. Redis durumu AuthorizationStore portunun arkasındadır. Example yazma handler sınıfları adlandırılmış ayrıcalıkları yan etkilerden önce denetler.

ExampleBoundedContext içindeki read/write portları, Doctrine ayrımı, memory adaptörleri ve modül-içi CQRS handler eşleştirmesi proje kararlarıyla tutarlıdır. Başlıca sorunlar Identity and Access sınırı, Shared çekirdeği, HTTP orkestrasyonu, messaging portlarının biçimi ve adaptör eşdeğerliğidir.

04 · Kritik bulgular

Öncelik, bağımlılık yönü ve değişiklik etkisine göre verildi

Kabul edilen CQRS kararı: Command ve query sözleşmeleri aynı bounded context içindeki tek handler sınıfını positional CQRSHandler attribute ile gösterir. Sözleşmeler bağımsız paket olarak dağıtılmaz. Bu nedenle eşleştirme bir sınır ihlali değil, testle korunması gereken modül-içi metadata kararıdır.
Çözüldü · 01

Identity and Access application portunu atlıyor

HTTP controller ve middleware artık TokenIssuer ve TokenValidator portlarına bağlıdır. Jwt, dışarıdan verilen codec ve AuthorizationStore ile yalnızca token akışını yönetir.

Middleware, tipli AccessControl nesnesini request içine koyar. Controller bu nesneyi command içine taşır. Application handler, gerekli ayrıcalığı transaction veya repository çağrısından önce denetler.

Kanıt: TokenIssuer.php, TokenValidator.php, AuthorizationStore.php, ChangeExampleHandler.php.

Uygulanan işlemTokenIssuer, TokenValidator ve AuthorizationStore portları eklendi. Yetkilendirme application handler sınırına taşındı.
Yüksek · 02

Domain ve Shared çekirdeği transport/framework bilgisi taşıyor

Domain exception sınıfları HTTP status ve Problem Details alanlarını taşır. Shared\Domain\DomainEvents Doctrine koleksiyonunu genişletir. Container-aware uygulamalar çekirdek ad alanlarında durur.

Kanıt: Shared/Domain/Exception/DomainException.php:7-17, AuthorizationExpired.php:11-14, Shared/Domain/DomainEvents.php:7,12, ContainerAwareDomainEventPublisher.php:9-38.

Önerilen işlemSaf domain hataları üretin. HTTP adapter içinde Problem Details eşlemesi yapın. Native collection kullanın. Container-aware sınıfları Infrastructure altına taşıyın.
Yüksek · 03

HTTP adaptörleri use-case orkestrasyonu ve eksik doğrulama yapıyor

PATCH ve DELETE action’ları önce query çalıştırır, 404 kararı verir ve sonra command çalıştırır. Başka bir giriş adaptörü aynı akışı tekrar etmek zorunda kalır.

PATCH alanları typed setter çağrısından önce doğrulanmaz. Hatalı dış girdi TypeError ve genel 500 yanıtı üretebilir.

Kanıt: ChangeExampleDetails.php:38-54, RemoveExample.php:41-46, resources/platform/07-http-api.md:16.

Önerilen işlemHer action’dan tek bir application portu çağırın. Kimlik çözümleme ve hata kararını handler içine taşıyın. Tüm PATCH alanlarını sınırda doğrulayın.
Orta · 04

Portlar yön ve teknoloji ayrıntısını tam gizlemiyor

BackendbaseQueue hem publish hem consume işlemini aynı arayüzde toplar. Ham diziler ve mixed kullanır. Notify, getClient(): mixed ile vendor client nesnesini dışarı açar.

Kanıt: BackendbaseQueue.php:9-18, Notify.php:9-16.

Önerilen işlemMessagePublisher ve MessageConsumer portlarını ayırın. Typed message/result nesneleri kullanın. Vendor client erişimini kaldırın.
Orta · 05

Politika concrete adaptörlerin içine yerleşmiş

Retry sayısı, permanent/transient kararları, outbox backoff ve yayın orkestrasyonu Doctrine adaptörlerinde uygulanır. Mekanizma ile politika aynı sınırlarda birleşir.

Kanıt: DoctrineQueueMessageFailurePolicy.php:14-43, DoctrineOutboxRelay.php:18-44,124-142.

Önerilen işlemRetry ve relay kararlarını application servisine taşıyın. Persistence adapter yalnız claim, kayıt ve durum güncelleme mekanizmasını uygulasın.
Orta · 06

Adaptörler aynı port için eşdeğer davranış vermiyor

Memory store yalnız ID ile kayıt yapar. Doctrine aktif lookup alanlarında eşsizlik uygular. Memory tabanlı testler, üretimde reddedilecek duplicate veriyi kabul edebilir.

Integration event üreticisi nested command alanı yayımlar. Kayıtlı external message DTO düz alanlar bekler. Producer → consumer uçtan uca contract testi yoktur.

Kanıt: Memory/ExampleStore.php:14-16, ExampleRecord.php:27-31, NewExampleAddedPayload.php:48-60, NewExampleAddedMessage.php:65-77.

Önerilen işlemAynı repository contract test paketini iki adaptöre çalıştırın. Üretici payload’ını kayıtlı consumer DTO’ya gerçek dispatcher üzerinden map eden test ekleyin.
Orta · 07

Mimari testler gerçek kaçakların bir bölümünü görmüyor

Mevcut testler temel domain purity, context isolation ve adapter direction kurallarını denetler. Ancak Application → Infrastructure, Shared framework importları ve inbound-adapter → outbound-adapter ilişkileri kapsam dışındadır. Testler ayrıca attribute hedefinin aynı context içinde kalmasını ve doğru handler arayüzünü uygulamasını genel bir kuralla doğrulamaz.

Kanıt: AdapterDirectionTest.php:17-29, FrameworkImportBoundaryTest.php:33-41, BoundedContextDependencies.php:14-31.

Önerilen işlemApplication, Shared core ve iki adaptör yönü için ayrı dependency testleri ekleyin. CQRS ve domain-listener attribute hedeflerini aynı context, tek positional hedef, doğru arayüz ve container çözümlemesi kurallarıyla koruyun.

05 · Güçlü taraflar

Mevcut iyi sınırlar korunmalı

Context-owned repository portları

Application handler’lar Doctrine yerine bounded context sözleşmelerine bağlıdır.

Read/write ayrımı

Read modelleri ile aggregate persistence davranışı farklı portlarda tutulur.

ORM izolasyonu

Domain aggregate üzerinde Doctrine attribute yoktur. ORM record ayrı bir mapper görevi görür.

Değiştirilebilir adaptör hedefi

Doctrine ve memory adaptörleri aynı proje arayüzlerini uygular.

Transactional messaging

Outbox, inbox ve external-effect işlemleri proje-owned portlar ve transaction sınırları kullanır.

Çalışan mimari korumalar

AST tabanlı testler temel yön ihlallerinin önemli bir bölümünü otomatik olarak yakalar.

Örnek kanıt: AddNewExampleHandler.php:21-25, Doctrine/ExampleWriteRepository.php:13-34, config/dependencies/doctrine.php:47-53.

06 · Düzeltme sırası

Önce kimlik ve Shared sınırları, sonra use-case akışı

  1. Identity and Access sınırını kurun. Token ve authorization portları ekleyin. HTTP, JWT ve Redis rollerini ayırın.
  2. Shared çekirdeğini saflaştırın. HTTP Problem Details eşlemesini dışarı taşıyın. Doctrine collection ve container-aware sınıfları çekirdekten çıkarın.
  3. Bir giriş, bir use case kuralını uygulayın. Controller içindeki query → command orkestrasyonunu application handler içine taşıyın.
  4. Messaging portlarını daraltın. Publish ve consume yönlerini ayırın. Ham diziler yerine typed message/result nesneleri kullanın.
  5. Adaptör eşdeğerliğini test edin. Memory/Doctrine contract suite ve producer/consumer message mapping testi ekleyin.
  6. Mimari testleri genişletin. Application, Shared core ve adapter-to-adapter bağımlılıklarını koruyun. İzin verilen attribute eşleştirmelerini aynı-context ve doğru-arayüz kurallarıyla sınırlandırın.
Başarı ölçütü: HTTP, CLI veya queue adaptörü değiştiğinde application/domain kodu değişmemeli. Doctrine, Redis veya broker değiştiğinde giriş adaptörleri değişmemeli.
