Overview

Backendbase uses the transactional outbox pattern for integration events. Consumers use inbox records to stop duplicate database work.

At least once

A broker or relay failure can cause duplicate delivery. Consumers must remain idempotent.

Atomic producer

The domain write and outbox insert commit in one database transaction.

Two drivers

Set BACKENDBASE_QUEUE_DRIVER to rabbitmq or sqs.

Delivery contract The system favors durable publication and safe duplicate handling. It does not provide exactly-once delivery.

Quick start

Use RabbitMQ for the local stack. Run migrations before any service writes integration events.

  1. Start MySQL and RabbitMQ. 
    docker compose up -d mysql rabbitmq
  2. Apply the message table migrations. 
    bin/doctrine migrations:migrate --no-interaction
  3. Start the outbox relay. 
    bin/backendbase outbox:relay --limit=100
  4. Start the integration-event consumer. 
    bin/backendbase queue:consume backendbase-queue
  5. Check queue publication health. 
    bin/backendbase outbox:status --max-pending-age=300
RabbitMQ management console Open http://127.0.0.1:15672 for the local Docker service. The default local user and password are backendbase.

Architecture

The database separates business completion from broker availability.

Producer and outbox flow

An integration event carries a stable event name, a version, an occurrence time, and a JSON-compatible payload.

  1. The command handler passes database work to IntegrationEventTransaction::execute().
  2. IntegrationEventTransaction::execute() starts a Doctrine transaction.
  3. The callback reads or changes domain state and can run synchronous domain listeners.
  4. The callback returns the complete IntegrationEvent.
  5. The transaction inserts the event into integration_event_outbox.
  6. The transaction commits both changes or rolls back both changes.
  7. The relay later claims the oldest available row and publishes it.

Producer pattern

$this->integrationEventTransaction->execute(
    function () use ($example): NewExampleAdded {
        $this->exampleRepository->add($example);

        return new NewExampleAdded(new NewExampleAddedPayload(/* ... */));
    },
);
Keep external input and output outside the transaction The transactional callback must not call a network service, process, or filesystem.

Relay state flow

Parallel relay safety

MySQL uses FOR UPDATE SKIP LOCKED. Each relay also writes a 60-second claim token.

Duplicate window

A publish can succeed before the database marks the row published. The next relay can publish it again.

Policy and mechanism are separate OutboxRelayService owns the relay loop, claim duration, publication outcome, and retry delay. DoctrineOutboxMessageStore only claims rows and applies supplied status updates.

Message envelope

Both adapters produce the same typed Message. Consumers receive no vendor object or transport array.

    "command": {

Transport difference

RabbitMQ wire body

messageId is an Advanced Message Queuing Protocol (AMQP) message property.

{
  "messageBody": "Example_NewExampleAdded",
  "eventVersion": "1.0",
  "data": {"exampleId": "0198..."}
}

SQS wire body

messageId and tag are in the JSON body.

{
  "messageBody": "Example_NewExampleAdded",
  "messageId": "0198...",
  "eventVersion": "1.0",
  "data": {"exampleId": "0198..."},
  "tag": "backendbase-queue"
}

Consumer and inbox flow

The integration consumer appends _Event to the producer event name. It then maps the versioned payload and dispatches external subscribers.

Integration subscriber behavior

  • The processor changes Example_NewExampleAdded to Example_NewExampleAdded_Event.
  • The registry selects a message class by event name and event version.
  • Valinor maps the payload into the versioned EventMessage class.
  • The event manager dispatches only ExternalIntegrationEventSubscriber implementations.
  • The inbox commits the database mutation and processed_at in one transaction.

QueueMessageFailureService owns permanent, transient, and five-attempt decisions. DoctrineQueueMessageFailureStore only records, marks, and clears failure state.

External effects

Notification delivery cannot share a database transaction with the external provider. ExternalEffectInbox uses a 300-second claim instead.

StateConsumer resultReason
Already processedACKDo not send the effect again.
Another claim is activeRETRYWait for the active 300-second lease.
Provider call or completion write failsREJECTThe provider outcome can be unknown. Automatic retry could duplicate the effect.
Effect completes and recordsACKThe inbox stores processed_at.

Commands

Run every command from the project root.

CommandDefaults and limitsExit behavior
bin/backendbase outbox:relay --limit=100 Limit: 1–1000. Processes oldest available messages first. Returns failure when one or more publications fail.
bin/backendbase outbox:status --max-pending-age=300 Age must be a positive number of seconds. Returns failure for any retried row or an old pending row.
bin/backendbase integration-messages:cleanup --retention-days=30 --limit=1000 Retention: at least 30 days. Limit: 1–10000 per table. Deletes only published outbox, processed inbox, and dead-lettered failure rows.
bin/backendbase queue:consume [queue-name] Default queue: backendbase-queue. Wait: 20 seconds. Long-running process. Stop it with the process supervisor.

Consumer process examples

# Integration events
bin/backendbase queue:consume backendbase-queue
Use a process supervisor Run consumers with systemd, Supervisor, Kubernetes, or another service manager. Cron does not restart a failed long-running process reliably.

Cron commands

These Linux crontab entries run the finite maintenance commands.

Assumption The application path is /srv/backendbase/current. Change this path before installation. These examples also require flock.

Recommended crontab

SHELL=/bin/sh
PATH=/usr/local/bin:/usr/bin:/bin
APP_DIR=/srv/backendbase/current

# Publish pending outbox messages every minute. Skip overlapping runs.
* * * * * cd "$APP_DIR" && flock -n var/run/outbox-relay.lock bin/backendbase outbox:relay --limit=100 >> var/logs/outbox-relay.log 2>&1

# Check outbox health every five minutes.
*/5 * * * * cd "$APP_DIR" && bin/backendbase outbox:status --max-pending-age=300 >> var/logs/outbox-status.log 2>&1

# Delete old completed message records each day at 02:17.
17 2 * * * cd "$APP_DIR" && flock -n var/run/integration-messages-cleanup.lock bin/backendbase integration-messages:cleanup --retention-days=30 --limit=1000 >> var/logs/integration-messages-cleanup.log 2>&1

Install and verify

# Create the lock and log directories as the application user.
cd /srv/backendbase/current
install -d -m 0750 var/run var/logs

# Edit the application user's crontab.
crontab -e

# Confirm the installed entries.
crontab -l

# Run each finite command once before waiting for cron.
cd /srv/backendbase/current
bin/backendbase outbox:relay --limit=100
bin/backendbase outbox:status --max-pending-age=300
bin/backendbase integration-messages:cleanup --retention-days=30 --limit=1000

Database records

Five migrations create and extend three message-control tables.

integration_event_outbox

Stores events until publication completes.

  • Identity: id
  • Contract: event_name, event_version, payload
  • Timing: occurred_at, created_at, available_at, published_at
  • Retry: attempts, last_error
  • Lease: claim_token, claim_until

integration_event_inbox

Stops repeated work for one consumer and message ID.

  • Primary key: consumer_name + message_id
  • Event: event_name
  • Timing: received_at, processed_at
  • External-effect lease: claim_token, claimed_until

integration_event_delivery_failure

Tracks bounded consumer retries.

  • Primary key: consumer_name + message_id
  • Count: attempts
  • Cause: last_failure_type
  • Timing: last_failed_at, dead_lettered_at

Retention rules

The cleanup command removes only terminal records older than the cutoff.

  • Outbox: published_at is old.
  • Inbox: processed_at is old.
  • Failure: dead_lettered_at is old.

Add a new integration event

Use the example bounded context as the working reference.

  1. Create the producer contract. Implement IntegrationEvent and use IntegrationEventTrait.
  2. Declare stable constants. Add EVENT_TYPE, EVENT_VERSION, and IS_MESSAGING_EVENT = true.
  3. Create a versioned payload. Keep producer payloads under Contracts/IntegrationEvents/V1.
  4. Write through the outbox transaction. Pass domain work to IntegrationEventTransaction::execute().
  5. Create the consumer message contract. Place it under Contracts/ExternalIntegrationEvents/V1.
  6. Create the external subscriber. Implement ExternalIntegrationEventSubscriber. Subscribe to <producer EVENT_TYPE>_Event.
  7. Register the contract and subscriber. Add events, subscriberFQCN, messageFQCN, and eventVersion to the bounded-context ServiceProvider.
  8. Test success, duplicate, invalid, and failure paths. Verify the handler outcome and database records.

Registration shape

[
    'events' => NewExampleAddedExternalSubscriber::getSubscribedEvents(),
    'subscriberFQCN' => NewExampleAddedExternalSubscriber::class,
    'messageFQCN' => NewExampleAddedMessage::class,
    'eventVersion' => NewExampleAdded::EVENT_VERSION,
]

Operations and recovery

Use the database state and broker state together during diagnosis.

SymptomCheckAction
Pending count grows. Run outbox:status. Check relay logs and broker access. Restore the broker or credentials. Run outbox:relay again.
Retried outbox rows exist. Inspect attempts, last_error, and available_at. Fix publication. The scheduled relay will retry automatically.
Consumer repeats one message. Inspect integration_event_delivery_failure and application logs. Fix the subscriber failure before replay.
RabbitMQ dead-letter queue grows. Inspect <queue>.dead-letter and failure type records. Fix the cause. Replay messages through a controlled process.
External effect has unknown outcome. Check the provider using the message ID and provider records. Resolve it manually. Do not replay until duplicate risk is known.
Cleanup deletes nothing. Confirm terminal timestamps are older than the retention cutoff. Do not lower retention below 30 days.

Useful database checks

SELECT id, event_name, event_version, attempts, available_at, claim_until, last_error
FROM integration_event_outbox
WHERE published_at IS NULL
ORDER BY created_at ASC;

SELECT consumer_name, message_id, attempts, last_failure_type, dead_lettered_at
FROM integration_event_delivery_failure
ORDER BY last_failed_at DESC;

SELECT consumer_name, message_id, event_name, processed_at, claimed_until
FROM integration_event_inbox
ORDER BY received_at DESC;
Do not edit message-control rows during normal recovery Manual deletion can remove idempotency evidence. Manual timestamp changes can cause duplicate publication or external effects.

Current limits and important behavior

These points describe the current source. Treat them as deployment constraints.

Notification consumer is absent

The source does not register a notification queue consumer or define a complete queued notification message.

Result: Add a consumer only with a complete message contract and a compatible provider.

SQS REJECT does not delete

The SQS adapter deletes only ACK messages. RETRY and REJECT both wait for the visibility timeout.

Result: A redrive policy is required to stop permanent redelivery.

RabbitMQ retries are immediate

RETRY uses negative acknowledgment with requeue. The adapter does not add a retry delay.

Result: A failing consumer can reach five attempts quickly.

Outbox uses the default route

OutboxMessagePublisher does not pass a queue or routing key. The selected adapter uses its configured default queue.

Result: Route events by service configuration, not per outbox row.

No automatic dead-letter replay

The application tracks terminal failures but provides no replay command.

Result: Validate and replay dead letters through an approved operational process.

Outbox has no terminal attempt limit

Publication failures remain pending and retry with a delay up to 256 seconds.

Result: Monitor old pending rows and correct the underlying failure.
