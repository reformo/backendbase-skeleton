Bounded Contexts

Keep one business model, its use cases, contracts, adapters, registration, and module tests in one movable unit.

Overview

A bounded context gives one business model a clear language and ownership boundary. Backendbase represents that boundary as a module under src/Backendbase/Domain/{ContextName}.

Own

Business meaning

Keep aggregates, domain rules, contracts, read models, and event schemas with the context that defines them.

Expose

Stable contracts

HTTP adapters and shared runtime services enter through commands, queries, ports, and event contracts.

Compose

Runtime wiring

A context ServiceProvider binds its ports, maps its handlers, and registers its integration event subscribers.

Reference implementation Use ExampleCatalog as the current pattern. No Content context exists in the current source. Name new contexts after their business capability. Omit Context and BoundedContext suffixes. The Example prefix identifies this demonstration context. Its entity is Entry. Reuse the structure with the target project's business names.

A directory under Domain is not automatically a complete registered context. Runtime discovery requires the expected service provider file.

Boundary model

The consumer adapter stays outside the context. It sends a contract inward. The application layer selects domain behavior and a port. The adapter implements that port.

Enforced platform boundary SharedDependencyBoundaryTest prevents Shared from importing Application, Domain, or Infrastructure. This keeps the shared runtime below application modules.

Module anatomy

A complete module keeps these parts under one context root. Create only the folders that the context needs.

├── Contracts/
│   ├── Command/                  # State-change inputs
│   ├── Query/                    # Read inputs
│   ├── ReadModel/                # Query results
│   ├── DomainEvents/             # In-process domain notifications

│   └── ExternalIntegrationEvents/# Versioned incoming message carriers
├── Application/

│   ├── QueryHandlers/            # Read orchestration
│   ├── DomainEventListener/
│   ├── IntegrationEventSubscribers/

│   ├── Doctrine/                 # Production read/write adapters

Port definitions

public static function getDefinitions(): iterable
{
    return [
        EntryReadRepository::class
            => DoctrineEntryReadRepository::class,
        EntryWriteRepository::class
            => DoctrineEntryWriteRepository::class,
    ];
}

Subscriber metadata

public static function getIntegrationEventSubscribers(): iterable
{
    return [[
        'events' => Subscriber::getSubscribedEvents(),
        'subscriberFQCN' => Subscriber::class,
        'messageFQCN' => MessageV1::class,
        'eventVersion' => Event::EVENT_VERSION,
    ]];
}

ServiceProvider::getHandlers() maps each command and query class to one application handler class for registry resolution.

No Composer mapping change is required for a normal context. The existing Backendbase\ PSR-4 mapping covers every context directory.

Write path

The reference write path puts behavior on the aggregate and persistence behind a write port.

01HTTP action
Validate input and create a command.
02Command bus
Resolve the handler from the configured source.
03Handler
Load or create the aggregate.
04Aggregate
Apply the business operation.
05Write port
Map and persist through Doctrine.

AddEntryHandler, ChangeEntryHandler, and RemoveEntryHandler return an event through IntegrationEventTransaction. It runs local subscribers before commit and writes the outbox when DELIVER_VIA_QUEUE is true. All participating database writes share that transaction.

Do not bypass the context An HTTP action must not update a Doctrine record directly. A persistence adapter must not decide how an aggregate changes.

Read path

The read path does not reconstitute an aggregate. It builds a projection through a read port.

01HTTP action
Validate input and create a query.
02Query bus
Resolve the query handler.
03Handler
Call the context read port.
04DBAL adapter
Run plain SQL for the use case.
05Read model
Return typed response data.

The example read adapter returns EntryDetails, EntryPage, EntryGroupPage, and identifiers. It filters removed records in SQL.

Persistence adapters

Read side

Doctrine DBAL and SQL

  • Accept query contracts through EntryReadRepository.
  • Use use-case-specific SQL.
  • Map rows with EntryReadModelMapper.
  • Return context read models, not Doctrine records.
Write side

Doctrine ORM and records

  • Accept aggregates through EntryWriteRepository.
  • Map with EntryRecord::fromDomain() and toDomain().
  • Synchronize storage state after domain behavior runs.
  • Throw a context-safe error when an active record is absent.

Both paths use example_table, but they use separate ports and adapters. Memory adapters share EntryStore for isolated tests. The memory store enforces the same active lookup identity uniqueness as Doctrine.

Doctrine discovery PathFinder::doctrineEntityPaths() discovers Domain/*/Adapters/Persistence/Doctrine/Entity and one additional nested module depth.

Context communication

The reference module demonstrates asynchronous communication through integration event contracts.

Domain event

Use an in-process event for behavior that belongs to the same business operation and service.

Producer integration event

Store a versioned event with the database change. Let the outbox relay publish it.

External event carrier

Map an incoming producer event to a versioned message class before an external subscriber handles it.

Place internal subscribers under Application/IntegrationEventSubscribers. Place external subscribers under Application/ExternalIntegrationEventSubscribers/{SourceService}.

No synchronous cross-context pattern is demonstrated The source tree does not provide a reference gateway for direct synchronous context calls. Avoid importing another context's application or adapter internals.

HTTP boundary

The HTTP adapter belongs under Infrastructure/Inbound, not inside the bounded context. This adapter translates transport data into context contracts.

The adapter can

  • Read PSR-7 request data.
  • Sanitize and validate external input.
  • Invoke one application operation through a command, query, or write-result orchestrator.
  • Dispatch one bus and shape an HTTP response.

The context owns

  • Business language and invariants.
  • Use-case orchestration.
  • Repository ports and read models.
  • Domain and integration event contracts.

ExampleApi is the only current consumer API. Each controller creates one context contract and dispatches it through the matching shared bus.

Testing strategy

Module-local tests

Keep tests that belong to the module under the module Tests/ directory. These tests move with the context.

vendor/bin/phpunit \
  src/Backendbase/Domain/ExampleCatalog/Tests

Platform and integration tests

Keep architecture, shared, infrastructure, functional, and API-level tests under root tests/.

vendor/bin/phpunit \
  tests/Functional/EntryLifecycleTest.php \
  tests/Architecture/SharedDependencyBoundaryTest.php
  • Use memory adapters for fast use-case and lifecycle tests.
  • Use Doctrine SchemaTool and production metadata for ORM repository schemas.
  • Run one port-specific repository contract suite against both memory and Doctrine adapters.
  • Test command and query contracts as public entry points.
  • Test aggregate rules without transport or persistence dependencies.
  • Test event schemas when other services can consume them.

Add a bounded context

  1. Choose one clear business capability and a PascalCase context name.
  2. Create src/Backendbase/Domain/{ContextName}.
  3. Define aggregates, value objects, enums, and business rules under Domain.
  4. Define commands, queries, ports, read models, and event contracts under Contracts.
  5. Add handlers that orchestrate one use case each.
  6. Add Doctrine and memory adapters only for required ports.
  7. Add ServiceProvider.php and implement Backendbase\Shared\ServiceProvider.
  8. Add command and query mappings to ServiceProvider::getHandlers().
  9. Register port bindings and all event subscriber metadata in the service provider.
  10. Add module-local tests and required platform tests.
  11. Verify container boot, Doctrine metadata, the CQRS paths, and event registration.
Database boundary Create or change only the database structure that the user explicitly requests. Generate a Doctrine migration after repository behavior is final.

Review checklist

  • The context owns one clear business language.
  • Business rules are in domain objects.
  • Every command and query has a context registry mapping and no handler attribute.
  • Handlers use ports, not concrete Doctrine adapters.
  • Read SQL stays in a read adapter.
  • Write mapping stays in a write adapter.
  • The service provider binds each context port.
  • Every integration subscriber is registered.
  • External event carriers are versioned.
  • HTTP validation occurs before bus dispatch.
  • Module-local tests stay with the module.
  • Architecture and functional tests pass.
  • No context imports another context's adapters.
  • Database changes match the exact request.
