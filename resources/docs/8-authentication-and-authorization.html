01 · Overview

Two checks protect a private operation

Authentication proves the token state. Authorization decides whether the authenticated user can perform an operation.

Token ports

HTTP inputs issue and validate tokens through application ports. The JWT and Redis adapters stay behind these contracts.

Authorization middleware

Reads the bearer token and adds user, time zone, and access-control attributes to the request.

ACL

Allows a named privilege, full privileges, or the system-admin role.

Current scope: The implementation is a reference identity boundary. The ExampleApi authentication action is not production authentication.

03 · Request flow

Bearer validation enriches the request

  1. Clientsends bearer token
  2. Middlewareparses scheme + token
  3. JWTchecks cryptography + claims
  4. Redisconfirms token is active
  5. Requestreceives identity + access control
  6. Controllerdispatches the command
  7. Handlerchecks the named privilege

The middleware adds authorizedUserId, authorizedUserData, clientTimezone, and typed AccessControl. It also keeps the concrete Acl attribute for compatibility.

04 · Token issue

Token issue creates cryptographic and server-side state

  1. Create a random token identifier.
  2. Set issuer, audience, identifier claim, custom user claim, and expiry.
  3. Sign with HMAC SHA-256 and the Base64 signing key.
  4. Store JWT:{alias}:{jti} in Redis with a time-to-live.
  5. Store user data, token history, privileges, and claim metadata under the alias and user identifier.

The default alias is USER. The default issuer is backendbase-api. The default duration is 24 hours.

Demo authentication: POST /auth requires a valid email and a non-empty password. It creates a token for one fixed user but does not verify the password.

05 · Token validation

Redis enables immediate revocation

  • The token must parse as an unencrypted signed JWT.
  • The token identifier must be a non-empty string.
  • The Redis token key must exist.
  • The signature, current time, issuer, token identifier, and audience must validate.
  • The Redis user record must exist.

The clock permits 30 seconds of leeway. A failed validation attempts to delete the token key and raises AuthorizationExpired.

Operational dependency: JWT issue and validation require Redis and RedisJSON. A valid signature alone is not sufficient.

06 · Access control

Check one named privilege at the application boundary

$command->accessControl()->isAllowed(self::REQUIRED_PRIVILEGE);

The check succeeds when the user has the requested privilege, has full-privileges, or uses role system-admin. A denied check throws ResourceAccessForbidden with HTTP status 403.

Example write handlers require example.add, example.change, or example.remove. They check access before transaction or repository work.

Do not read the raw privilege array in controllers. Pass typed access control through the application input and enforce it in the handler.

07 · API keys

API-key validation depends on request attributes

ExampleApi middleware sets apiName, apiKeyHeaderName, and useIdentifierAsApiKey. ValidateApiKey then compares the request header with API settings.

Normal modeCompares the header with {api-name}.api-key. Only the configured public path prefixes skip this check.
Current state: ExampleApi comments out ValidateApiKey::class. OpenAPI and Bruno still declare and send the key.

08 · Route policy

Protect new endpoints by default

Group new consumer endpoints with AuthorizationMiddleware. Leave an endpoint public only for a clear bootstrap, callback, webhook, or public-information use case.

The current Example module protects POST, PATCH, and DELETE routes. Their application handlers also enforce named privileges. GET routes are not grouped with bearer authorization.

10 · Failure behavior

Security errors need stable public status codes

The ACL uses status 403. The current bearer middleware returns status 400 for a missing, malformed, expired, or invalid token. API-key failures also return 400.

Contract difference: OpenAPI lists 401 and 403 for authentication and authorization failures. The runtime currently returns 400 for several authentication failures.

11 · Current gaps

Known security limits

  • The authentication endpoint does not verify credentials.
  • API-key middleware is active, but its failures use 400 instead of 401 or 403.
  • Bearer failures use 400 instead of 401.
  • The time-zone header is passed directly to DateTimeZone.
  • ValidateApiKey contains public paths that do not belong to the current ExampleApi route set.
  • SessionMiddleware is available but is not part of the inspected ExampleApi middleware chain.

13 · Checklist

Review every security change

  • Credentials are verified before token issue.
  • Secrets are not logged or returned.
  • Issuer, audience, expiry, and Redis state are validated.
  • Routes have an explicit public or protected policy.
  • ACL checks use stable privilege names.
  • 401 and 403 responses match OpenAPI.
  • Failure paths have focused tests.
