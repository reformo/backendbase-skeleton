01 · Overview

HTTP operations use API-key protection

ExampleApi requires the configured API key for metadata and every Example read or write. Liveness and readiness remain public.

IdentityAndAccess owns global Accounts and realm-specific User and SystemAdmin actors. UserApi and SystemAdminApi expose separate authentication flows. Greeting HTTP endpoints remain absent.

04 · Internal access control

Keep the internal greeting privilege check

QueueGreeting requires a full name and typed Shared AccessControl. Its handler checks example.add before starting the integration-event transaction.

The caller must supply the interface implementation. Tests use interface doubles for allowed and denied calls. No HTTP route dispatches this command.

05 · API keys

API-key validation depends on request attributes

ExampleApi middleware sets apiName, apiKeyHeaderName, and useIdentifierAsApiKey before ValidateApiKey runs.

Normal mode compares Backendbase-Api-Key with example-api.api-key. Identifier mode requires a non-empty header.

Configured public path prefixes bypass validation. OPTIONS returns an empty 200 response.

06 · Route policy

Protect new endpoints by default

Use the existing API-key middleware for new consumer operations. Declare anonymous policy explicitly in routing and OpenAPI.

07 · Configuration

Keep the key outside source control

EXAMPLE_API_KEY supplies the expected API key through config/example-api/global.php. Do not log or return this value.

New identity configuration declares separate realm issuers, audiences, signing keys, encrypted factor keys, and bounded session lifetimes. The identity migration creates Account, User, Admin, and challenge records with assigned binary UUIDv7 identifiers.

08 · Failure behavior

Security errors use stable public responses

A missing or invalid API key returns 401 with code identity-access/api-key-invalid before command dispatch.

The shared ResourceAccessForbidden mapping remains available with status 403. Internal greeting denial stops the transaction.

09 · Current limits

Known limits

  • The API-key public-path list includes prefixes outside the current ExampleApi route set.
  • The shared OpenAPI headers are not all enforced at runtime.
  • CORS omits Accept-Language.

Databases that executed the removed account migration can still contain account and privilege tables. Review their schema and migration history before deployment.

Identity realms and session gates

Set X-Source-Id to user or system-admin. The trusted route selects USER or ADMIN authentication policy. A client header does not grant authority.

User registration creates one global Account and one User actor. Verify the Account email through a separate ownership challenge. Enroll a Time-based One-time Password (TOTP) factor before session issuance.

Admin enrollment requires an existing verified Account, invitation evidence, and separate approval evidence. An Admin cannot approve its own invitation. Both realms require password and TOTP authentication.

Login returns a short-lived JSON Web Token (JWT) only after Redis records both token and session allowlist entries. Request validation checks signature, issuer, audience, realm, actor type, expiry, both Redis records, and current Account and actor state.

Token revocation removes the current token entry. Logout removes token and session entries. Account closure disables the Account, increments its authentication version, and blocks both realms.

Local root operator commands record first-Admin invitation, approval, and lost-factor recovery evidence. Recovery requires ownership verification and new TOTP enrollment before a new session.

Protected actor mutations reload persisted authorization under Account-first locks after a target reference lookup. A concurrently removed Admin cannot restore itself through stale managed state.

Read the full identity policy. Review the User API contract and System Admin API contract.
