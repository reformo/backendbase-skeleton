01 · Overview

Each inbound API has an explicit security policy

ExampleApi requires the configured API key for metadata, Authentication, Identity, and Example operations. All Example operations except getExampleByCriteria also require USER bearer authentication. Liveness and readiness remain public.

IdentityAndAccess owns global Accounts and realm-specific User and SystemAdmin actors. ExampleApi and UserApi share USER authentication and sessions. SystemAdminApi uses the separate ADMIN realm. Greeting HTTP endpoints remain absent.

All three APIs use trusted realm policies and JSON Web Tokens (JWTs) on protected identity routes. See identity realms for session and database gates.

04 · Internal access control

Keep the internal greeting privilege check

QueueGreeting requires a full name and typed Shared AccessControl. Its handler checks example.add before starting the integration-event transaction.

The caller must supply the interface implementation. Tests use interface doubles for allowed and denied calls. No HTTP route dispatches this command.

05 · API keys

API-key validation depends on request attributes

ExampleApi middleware sets apiName, apiKeyHeaderName, and useIdentifierAsApiKey before ValidateApiKey runs.

Normal mode compares Backendbase-Api-Key with example-api.api-key. Identifier mode requires a non-empty header.

Configured public path prefixes bypass validation. OPTIONS returns an empty 200 response.

06 · Route policy

Protect new endpoints by default

Apply the target API's existing security policy. Example operations require the API key. All except getExampleByCriteria also require a USER bearer token. Identity operations use trusted USER or ADMIN policies. Declare anonymous policy explicitly in routing and OpenAPI.

Metadata and all six Example routes require an API key. Liveness and readiness use security: [].

Identity, Administration, and protected Example groups add RealmAuthentication, then RealmPolicy. Slim executes the last added middleware first. The realm therefore exists before authentication runs. Endpoint action and contact policies execute after group authentication.

Public Authentication groups apply RealmPolicy and write replay through Idempotency. Login and public contact verification do not require a bearer token. ExampleApi Authentication routes retain the API-key requirement. Health and preflight routes remain outside protected groups.

07 · Configuration

Keep the key outside source control

EXAMPLE_API_KEY supplies the expected API key through config/example-api/global.php. Do not log or return this value.

New identity configuration declares separate realm issuers, audiences, signing keys, ownership proof hash keys, and bounded session lifetimes. The identity migration creates Account, User, Admin, and contact verification records with assigned binary UUIDv7 identifiers.

08 · Failure behavior

Security errors use stable public responses

A missing or invalid API key returns 401 with code identity-access/api-key-invalid before command dispatch. Missing or invalid bearer credentials return 401. Unavailable authentication state returns 503.

The shared ResourceAccessForbidden mapping remains available with status 403. Internal greeting denial stops the transaction.

09 · Current limits

Known limits

  • The API-key public-path list includes prefixes outside the current ExampleApi route set.
  • Runtime validation accepts missing trace and timezone headers. Supplied values must pass format validation.
  • The security workflow preserves ExampleApi checks and defines HTTP checks for all 31 identity operations. Separate authenticated scans cover protected identity reads and metadata. See the exact scope.
  • Production revocation durability, managed secret injection, and recovery require target-specific acceptance evidence.

All three API header configurations allow Accept-Language. See the current assessment and identity acceptance procedure.

Databases that executed the removed account migration can still contain account and privilege tables. Review their schema and migration history before deployment.

Identity realms and session gates

Set X-Source-Id to example, user, or system-admin. The selected API's group sets USER or ADMIN through RealmPolicy. A client header does not grant authority.

Require email and mobile input before User registration. Verify mobile less than 12 hours before registration. Registration resolves evidence by contact values and context. It consumes mobile and matching fresh optional email evidence with Account and User creation in one transaction. Authenticated Users can verify their stored email through /identity/contact-verifications after login. Admin contact verification remains optional after enrollment and login. See contact verification for the complete contract.

Admin enrollment requires an existing verified Account, invitation evidence, and separate approval evidence. An Admin cannot approve its own invitation. Both realms use password authentication.

Account state records ownership with the boolean ownershipVerified. User registration sets it after the required mobile proof passes. Email verification remains separate and optional. The trusted initial Admin bootstrap also confirms ownership. Login and session validation require this flag, Account enablement, and the applicable actor checks.

Immutable identity state primitives validate stored JSON before domain use. Unknown, missing, or mistyped fields cause an explicit failure. Aggregate methods retain authorization decisions. Contact state serialization includes internal data and must not become a public response or diagnostic log.

Accounts store the Argon2id password hash directly in required account.password_hash VARCHAR(255). The credential store reads and writes a string under the existing Account locks. The consolidated installation migration creates this column directly. Existing databases with credential JSON need separate schema and data adoption.

POST /auth/login returns a session result with a short-lived JSON Web Token (JWT) only after Redis records both token and session allowlist entries. Request validation checks signature, issuer, audience, realm, actor type, expiry, both Redis records, and current Account and actor state.

The existing RedisJSON library stores token and session objects through atomic Lua scripts. Activation applies key-level EXPIRE after each JSON.SET, using the remaining JWT lifetime. Reads do not renew expiry. Existing string records remain readable until expiry. Account block markers remain strings.

The same script applies EXPIREAT after EXPIRE to retain the JWT's exact expiration deadline.

Token revocation removes the current token entry. Logout removes token and session entries. Account closure disables the Account, increments its authentication version, and blocks both realms.

Local root operator commands store first-Admin invitation and approval evidence in Admin state. Operator setup and manual seeding use the same database-scoped MySQL lock. Operator approval requires the sole pending Admin. Separate operator names and action timestamps have no persistence table. TOTP enrollment and recovery are removed.

Protected actor mutations reload persisted authorization under Account-first locks after a target reference lookup. A concurrently removed Admin cannot restore itself through stale managed state.

Read the full identity policy. Review the User API contract and System Admin API contract.

Account profiles support optional first and last names. The approved initial Admin uses the manual database:seed-admin command. It requires local root authority and records bootstrap evidence without issuing a session. See the operator procedure for password-file input and repeat-run behavior.
