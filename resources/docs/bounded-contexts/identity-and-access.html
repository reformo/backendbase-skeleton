01 · For every reader

Identify the Account and check its current access

IdentityAndAccess is the application area that owns Accounts, passwords, User and Admin access, contact verification, tokens, and sessions.

A bounded context is an area with its own business rules and data ownership. This context decides whether a person can sign in and use an authenticated identity.

Applications use an application programming interface (API) to request registration, login, and other identity operations.

1Shared Account for credentials and contacts
2Separate authentication realms: USER and ADMIN

Product and support: Start with the Account model, registration, sessions, Admin enrollment, and support decisions.

Developers: Read the API, transaction, data, and retry rules.

Three separate facts: Contact verification proves control of a contact. A password proves knowledge of a credential. Admin approval grants Admin eligibility.

02 · Account model

One Account can have User access and Admin access

An actor is the Account's access record in a realm. A realm is a separate authentication area with its own token trust settings.

User and Admin actors have different identifiers. The Account identifier refers to their shared credentials and contacts. A USER token does not grant ADMIN access.

TermMeaningImportant distinction
AccountThe shared identity and credentials.Closing it blocks access across both realms.
ActorUser or Admin eligibility for that Account.Removing one actor does not release the Account's contacts.
TokenA signed credential supplied on API requests.Signature validity alone does not establish current access.
SessionA stored login state checked with its token.Token and session records must both exist in Redis.

Email and mobile are globally unique among active Accounts. Account closure releases those active contact reservations. Removed actors remain retained records.

03 · Registration and contact proof

Apply the registration verification policy

Set BACKENDBASE_IDENTITY_REGISTRATION_REQUIRE_MOBILE_VERIFICATION and BACKENDBASE_IDENTITY_REGISTRATION_REQUIRE_EMAIL_VERIFICATION to exactly true or false. Defaults are true and false. See configuration and rollout rules.

  1. Request a codeSupply mobile and a secret verification context.
  2. Confirm mobileSupply the context and the six-digit code.
  3. RegisterSupply email, mobile, password, and the same context.
  4. Log inUse email or mobile and the password.

Email and mobile input are required. The default flow shown above requires mobile proof. Two independent settings can require mobile, email, both, or neither. Email verification remains available after login.

Each required proof must be less than 12 hours old at registration. Proof exactly 12 hours old is expired. Normal login remains available after this registration window.

Successful registration creates the Account and User. Login is a separate operation that issues a session.

Developer details: values, context, and atomic registration
  • Email uses lowercase ASCII. Mobile uses E.164: a plus sign and 2 to 15 digits. Domestic formatting and inferred country codes are rejected.
  • Passwords contain 12 to 128 UTF-8 characters, at most 512 bytes, and no null byte. Passwords are not trimmed.
  • Optional firstName and lastName contain 1 to 160 UTF-8 characters when supplied. Empty values, surrounding spaces, and control characters are rejected.
  • The client creates verificationContextToken from 32 random bytes encoded as canonical unpadded base64url. The result contains 43 characters.
  • Registration accepts contact values and a context token. The token may be omitted or null only when neither proof is required. Contact record identifiers are rejected.

When a context is supplied, the workflow locks email evidence before mobile evidence, then reads the authorization time. One MySQL transaction consumes proof and creates identity records.

Matching fresh optional evidence is consumed too. Missing or unusable optional evidence does not block registration. Concurrent registration permits one successful proof consumption.

Successful registration stores registrationAccepted: true. It stores ownershipVerified: true only when evidence is consumed. Registration without proof leaves ownership false. Later email verification remains recorded separately.

Verification after login

An authenticated User can verify the Account's stored email. The server selects the destination. The client cannot use this flow to replace the email or verify another Account.

Admin verification is optional. It verifies stored contacts and does not grant Admin approval. Verification preserves existing ownership and sessions.

04 · Login and session lifecycle

Each protected request checks current state

Login accepts the Account email or mobile and password. User login requires stored registration acceptance. Admin login requires verified ownership. Both require an enabled Account and an eligible actor. Legacy Accounts retain their earlier authorization results. Configuration changes do not invalidate existing sessions.

An invited Admin must be approved before login. A successful User login does not create Admin access.

An allowlist records permitted access. Redis stores permitted tokens and sessions. MySQL stores current Account and actor state.

  1. Signed tokenVerify signature and trusted key identifier.
  2. Realm and timeCheck issuer, audience, type, and expiry.
  3. Redis stateRequire matching token and session records.
  4. MySQL stateCheck current Account and actor eligibility.
  5. Operation policyCheck authority for the requested action.

A JSON Web Token (JWT) is signed, but its claims can still be read. Current tokens contain identifiers and authentication state. They do not contain email, mobile, or profile names.

The default token lifetime is 900 seconds. The supported range is 60 to 3,600 seconds. Reads and replay do not renew it. No refresh-token flow is provided.

ActionEffectSupport implication
Revoke current tokenRemove the current token allowlist record.That token cannot authenticate. Other independent sessions can remain valid.
End current sessionRemove the session and current token records.The current session can no longer authenticate.
Remove an actorMark that actor as removed. Current MySQL checks reject it.The Account and its contact reservations remain.
Restore an actorClear the actor's removal marker. Current Account and approval gates still apply.Restoration does not create a new session or token.
Close AccountDisable the Account, increase its authentication version, and request revocation across both realms.Current MySQL state rejects old tokens even if Redis revocation fails.
Actor restoration can restore old access. Removal does not delete the actor's Redis records. An existing unexpired token can become usable again after restoration when all current gates pass.
Developer details: token claims and Redis records

sub identifies the actor. accountId identifies its Account. realm is USER or ADMIN. actorType is User or SystemAdmin.

jti identifies the token. sid identifies the session. authVersion must match the current Account version.

Other claims are iss, aud, iat, nbf, and exp. Headers include alg: HS256, typ: JWT, and the configured kid.

Redis uses Account-scoped realm keys. The token and session values are RedisJSON objects. A Lua script creates both records atomically and sets expiry to the JWT deadline.

Redis stores identity claims rather than the signed token string. Existing compatible string records remain readable until their original expiry.

05 · Admin enrollment and operator work

Use separate invitation and approval actions

  1. Establish an enabled Account with verified ownership.
  2. An authorized Admin invites that Account with an invitation evidence reference.
  3. An authorized Admin approves the invited actor with a different approval evidence reference.
  4. The approved actor can log in through the ADMIN API with the Account credentials.

The target Admin cannot approve its own enrollment. The same existing Admin can invite and approve another Admin when the evidence references differ.

Any requirement for different staff members must be enforced by the surrounding approval process. Separate evidence does not by itself establish that staff separation.

First-Admin bootstrap

Before any Admin row exists, local operator commands can invite and approve the first Admin. Preview is the default. Applying an action requires local root authority on the identified target.

Registration, administration, contact, and operator inputs store typed readonly fields. Contact input uses named constructor arguments. Application services consume these fields directly.

ApplyOperatorActionHandler calls OperatorRuntime, which supplies the clock to OperatorWorkflow. The handler records the result after successful completion.

identity:operator requires an action, target identifier, operator label, and the applicable evidence. Invitation and approval use separate commands.

A database-scoped MySQL lock serializes bootstrap and manual seeding. Approval requires the sole Admin row to be pending and active. Removed Admin rows still count.

Operator details: manual seeding and evidence limits

database:seed-admin is a manual bootstrap for the explicitly approved fixed initial identity. It is not a general Account or Admin creation tool.

Apply uses --password-file with a private file in mode 0600. The command does not trim or print the password.

Mode 0600 permits file access only for its owner.

The seed attests ownership and creates an approved Admin. It creates no User actor, contact proof, or notification.

Operator commands issue no login token. Admin state retains invitation and approval references. There is no separate operator history table.

The --operator option is an invocation label. Keep any required staff approval and audit evidence in the authorized external records.

06 · For developers

Use the API surface for the intended realm

SurfaceRealmSelection and access
/user-apiUSERX-Source-Id: user. Public registration, login, and contact proof. Bearer token for protected identity flows.
/example-apiUSERX-Source-Id: example. Shares User credentials and sessions. ExampleApi also requires its API key on Authentication and Identity routes.

The client header selects a known API. Trusted route middleware selects the expected realm. A client cannot select extra authority through a header.

Retries are part of the write contract

All identity writes require Idempotency-Key. Reuse it with the exact request for retries. X-Request-Id remains a separate trace identifier.

Login replay returns the original token without renewing it. Contact replay avoids another message or proof consumption.

Authentication runs before protected replay. A successful logout, token revocation, or Account closure can therefore make its retry return 401.

Generic HTTP replay preserves the registration response for 24 hours. Without that matching retained replay, consumed registration proof causes a business conflict.

07 · Architecture and data

Keep business decisions in the owning context

The context lives under src/Backendbase/Domain/IdentityAndAccess. Its service provider binds ports and maps command and query handlers.

StorageOwner and purposeDeveloper rule
MySQL accountShared contacts, names, password hash, registration acceptance, ownership, enabled state, and authentication version.Keep Account identity separate from actor identity.
MySQL user and adminRealm-specific membership, approval, removal, and retained evidence.One actor of each type per Account, including removed rows.
MySQL contact_verificationContact, purpose, realm, context digest, code hash, deadlines, attempts, and consumption state.Do not expose its full internal state in responses or logs.
RedisToken/session allowlists, Account blocks, and verification reservations.Require matching token and session state. Reads do not renew expiry.
MySQL http_request_replayShared HTTP infrastructure stores request claims and encrypted results.Keep replay outside the context's application transaction.

Passwords use Argon2id in account.password_hash. Contact codes use a keyed hash. Raw verification context tokens and plaintext codes are not stored in the contact table.

Developer details: transactions, mapping, and HTTP adapters

Domain objects own eligibility and state transitions. Application workflows coordinate repositories, credentials, session activation, verification, and administration.

Doctrine adapters enforce Account-first locking and database uniqueness. Transient transaction retries use fresh entity managers. Registration preserves proof on rollback.

Protected actor changes reload persisted authority under locks. A concurrently removed Admin cannot restore itself through stale managed state.

Mapped JSON fields reconstruct immutable AccountState, ActorState, and ContactState values. Missing, mistyped, or unsupported fields fail explicitly.

Account and Actor retain typed snapshots that reuse these JSON values. ContactInfo retains ContactState. State changes preserve earlier snapshots.

Aggregates own contact membership, stored-contact selection, realm eligibility, and pending Admin approval checks.

Registration hashes the password before opening the identity transaction. Identity creation, credential storage, and proof consumption share that transaction.

HTTP controllers remain inside their owning inbound API. Shared HTTP helpers live outside the context's domain and application layers.

Success responses use descriptive keys such as registration, session, and contactInfo. Problem Details fields remain at the response root.

There is no shared MySQL/Redis transaction. Session activation and notification delivery can fail after database work. Recovery must inspect both persisted state and external evidence.

08 · Configuration

Keep three key purposes separate

Signing keys protect tokens. Contact proof keys protect verification hashes. The replay key encrypts stored HTTP results. Use separate generated secrets for these purposes.

All three key types require base64-encoded 32-byte values. Public example keys are for local development. Inject production secrets through the approved deployment mechanism.

09 · Deployment and recovery

Retain the state needed to verify existing work

  • JWT signing keys: Keep a previous verification key until tokens signed with it no longer need verification.
  • Contact proof keys: Retain issued keys through pending-code deadlines and the confirmed evidence recovery window of verifiedAt + 12 hours.
  • Replay encryption key: Follow the separate drain and reconciliation procedure. Changing it invalidates retained replay evidence.
  • Runtime configuration: Clear relevant caches and restart supervised workers after approved key injection changes.
  • Database history: Fresh installation applies all six current migrations. Older or divergent installations need a target-specific adoption plan.

When Redis loses revocation evidence

Redis replication is asynchronous. A promoted stale replica can lose acknowledged token or session revocations.

Current MySQL state still rejects closed Accounts and changed authentication versions. It cannot reconstruct a lost token-only revocation.

Use the authorized session recovery procedure to invalidate affected allowlists in both realms before reopening traffic. Require login for affected sessions.

The application uses a configured Redis endpoint. It does not discover the Sentinel primary automatically. Deployment infrastructure must provide or update that endpoint.

11 · Important limits

Plan processes around the current capability

  • No documented refresh-token, password-reset, time-based one-time password (TOTP) enrollment, or factor-recovery flow is provided.
  • There is no public Admin registration. Ordinary Admin enrollment starts from an existing verified Account.
  • Optional contact verification does not change stored contact values or grant Admin approval.
  • Contact quotas apply to verification operations. They are not a general password-login rate limiter.
  • The context implements User and Admin identity gates. Broader application privilege rules use the project's separate access-control contracts.
  • MySQL, Redis, and notification providers do not form one transaction. External delivery and failover need operational recovery.
  • Isolated fixture success does not establish production throughput, managed-service durability, or production recovery time.
