01 · Overview

The domain does not know Doctrine

Bounded-context contracts define persistence ports. Doctrine adapters implement those ports. Domain aggregates and read models remain independent from database records.

Write side

Doctrine ORM maps typed aggregate snapshots to records and saves state.

Read side

Doctrine DBAL runs explicit SQL and maps rows into immutable read models.

Schema side

Reviewed migrations own production schema changes. Seeders add approved reference data.

03 · Write persistence

Save aggregate state through a write port

EntryWriteRepository persists a new ExampleTable, loads active records by UUID, synchronizes a record from a typed EntrySnapshot, and flushes the entity manager.

  • add() maps a new aggregate with fromDomain().
  • getActive() reconstitutes an aggregate with toDomain().
  • save() synchronizes the existing record and flushes.
The adapter maps state. It must not decide how an example changes or whether a business operation is allowed.

04 · Read projections

Use DBAL and explicit SQL for query models

EntryReadRepository uses one table for identifier lookup, detail lookup, paginated groups, and paginated example lists. Group queries count all matching distinct groups and return EntryGroupPage. SQL applies the requested page size and offset without a 1,000-group result cap.

  • Bind all values as parameters.
  • Bind page size and offset as integers.
  • Filter removed records with deleted_at IS NULL.
  • Return context read models, not database rows or Doctrine entities.
  • Use stable ordering for pagination.
Trust boundary: EntryReadModelMapper rejects invalid persisted strings, integers, booleans, enums, dates, and JSON objects.

Every selective query must have a suitable primary, unique, or composite index. Review equality filters, ranges, joins, grouping, and stable ordering. Add missing required indexes, matching metadata, forward migrations, and regression checks in the same change. Document intentional full scans.

The runtime query inventory records existing coverage and the four required index additions. The consolidated installation migrations create two Example indexes and two message-first cleanup indexes. Identity lookups already use primary or unique keys.

SQLite plan checks do not prove MySQL optimizer selection or production speed. Verify representative EXPLAIN plans on an identified, prepared MySQL target. Do not add speculative or duplicate indexes.

05 · Record mapping

Records translate aggregate snapshots into columns

Derive each mapped Doctrine entity class name from its full table name in PascalCase. Preserve table prefixes and words: example_table maps to ExampleTable, and identity_account maps to IdentityAccount.

contact_info stores email and mobile verification evidence before User registration. Its unique context-slot index prevents duplicate contact requests. Registration locks both proof rows before it checks the twelve-hour deadline. It consumes both proofs in the Account and User transaction. Optional Admin verification uses bound evidence and preserves sessions and approval.

Every entity declares all mapped fields directly, including identifiers, versions, and timestamps. Entity classes have no parent class. Mapped fields must not come from traits or mapped superclasses. Interfaces and behavior-only traits can supply shared contracts or methods.

ExampleTable uses PHP attributes for its table, indexes, unique constraints, columns, generated columns, UUID, enum, JSON, timestamps, and soft removal state.

06 · Discovery and types

PathFinder discovers mapped entity directories

The runtime and Doctrine CLI use PathFinder::doctrineEntityPaths(). The CLI schema filter includes service tables and the Doctrine migration metadata table.

Discovery includes the shared entity directory only when it exists. Fresh checkouts can omit this empty directory. Context and nested module discovery remain available.

config/doctrine-types.php registers UUID, binary UUID, and JSON document types. The main container also registers custom MySQL DQL functions.

Run Doctrine commands from the project root. Entity and configuration discovery use relative paths.

07 · Migrations

Generate, review, and execute approved schema changes

The three consolidated migrations support fresh installations only. They create final messaging, Example, and identity schemas with the required indexes. Inspect completed tables and indexes after partial failure because MySQL DDL is non-transactional. See consolidation and adoption for the migration map and existing-database boundaries.

Identity Accounts require email and E.164 mobile. Nullable first_name and last_name columns preserve optional Account names with a 160-character limit. Each contact has an active-key unique index. User and Admin tables have no username columns. Actor history joins the retained Account through its primary key for contact fields. The fresh identity installation migration creates this schema directly.

The required password_hash VARCHAR(255) column stores the Account's Argon2id hash directly. Password hashes use no lookup index. Existing databases with credential JSON require a separate reviewed conversion and migration-history adoption plan.

Account state JSON stores ownershipVerified, enabled, and authVersion. Existing rows with the former owned key require a separate data conversion that preserves the boolean value. The rename adds no migration or database column.

  1. Finish the domain record and repository behavior.
  2. Make repository tests pass.
  3. Run bin/doctrine migrations:diff.
  4. Review every generated SQL statement.
  5. Keep only the schema requested by the feature.
  6. Use plain CREATE TABLE so unexpected existing tables stop the migration.
  7. Use IF NOT EXISTS only with an explicit adoption plan and exact schema validation.
  8. Identify the prepared target database and inspect every pending migration.
  9. Run bin/doctrine migrations:migrate --dry-run --no-interaction against that target.
  10. Apply only with explicit authority for that database and every pending statement.
  11. Verify the resulting schema after an approved application.

Feature implementation approval does not authorize database mutation. Report unavailable or unapproved targets as skipped verification. Use the manifest-backed deployment workflow for production.

Existing databases that executed this migration require a separate adoption plan before deployment. Compare their schema and migration records with the remaining migrations. Review any account-table or migration-record changes before applying them to an explicitly authorized database.

The first migration, Version20260823000000, creates all integration-event tables and indexes for a new database. Existing databases that ran the former five messaging migrations need a separate schema and migration-history reconciliation plan before using this rewritten history. Do not run the first migration against those tables.

Consolidated Example migration: Version20260823215059 creates example_table with its complete columns and indexes. It includes binary UUID keys, virtual public UUIDs, versions, microsecond timestamps, active uniqueness, and group and pagination indexes. The separate uniqueness migration Version20260825050000 has been removed.

Both remaining migrations use the non-transactional MySQL base. Example rollback drops the table. For partial failure, inspect the schema before choosing forward recovery or a separately approved rollback.

Databases that ran either former Example migration need a separate adoption plan. Inspect the table, generated columns, unique index, and recorded versions. If only table creation ran, compare the existing schema with the final definition before planning the uniqueness change. If both versions ran, verify the final schema before planning version-record reconciliation. Do not recreate an existing Example table or change migration records without explicit authority for that database.

Hard boundary: Do not add unrequested tables, columns, indexes, timestamps, status fields, or audit fields.

08 · Seeders

Seed only approved reference data

Seeders use the Backendbase\Seeders namespace and live under resources/database/Seeders. When a migration queues schema SQL with addSql(), call its seeder from postUp() after Doctrine executes that SQL.

  • Make each seeder idempotent with an existence check.
  • Seed reference or lookup data only.
  • Do not put environment-specific or test-only data in production seeders.
  • Do not invoke the reference EntrySeeder unless the feature explicitly needs that data.

The explicitly approved AdminSeeder is a manual bootstrap exception. It creates the initial named Account and Admin with separate invitation and approval evidence. The local root command database:seed-admin reads a password file. It never runs from a migration or release. Repeat runs preserve the existing password. The command creates no schema.

09 · Transactions

Use one transaction for state and its outbox event

IntegrationEventTransaction runs business work and dispatches the returned integration event before commit. Local subscribers run for both delivery modes. DELIVER_VIA_QUEUE = true also appends an outbox row through DoctrineIntegrationEventOutbox. Subscriber repositories and the outbox writer share the business connection. A failure rolls back all database writes. Inbox adapters coordinate consumer deduplication and external-effect state.

Example change and removal handlers resolve the active entry through the write port inside the integration-event transaction. They persist the change before returning its event.

10 · Database tests

Prove shared behavior and storage details

Run one behavioral repository contract suite unchanged against every adapter for the same port. The Example suite runs against memory and Doctrine adapters.

EntityFieldOwnershipTest checks production metadata for parent classes and inherited or trait-owned mapped fields. Compare metadata and generated schema SQL when field declarations move.

  • Test only behavior declared by the port. Applicable examples include lookup, filtering, ordering, pagination, uniqueness, replacement, and removal.
  • Create ORM test schemas with Doctrine SchemaTool and production mapping metadata.
  • Test aggregate-to-record and record-to-aggregate mapping.
  • Test DBAL filtering, null handling, ordering, pagination, and malformed persisted data.
  • Test migration SQL and custom Doctrine functions.
  • Test seeders twice to prove idempotency.
  • Test commit and rollback behavior for transaction adapters.

11 · Rules

Keep storage rules explicit

  • Handlers depend on ports, not concrete Doctrine classes.
  • Controllers do not run SQL or use the entity manager.
  • Read adapters validate persisted data before creating read models.
  • Write adapters map aggregate state without business decisions.
  • Adapters for one port return the same results and context-safe errors for shared behavior.
  • Database changes require explicit feature scope and reviewed migrations.
  • Migration and seeder behavior has automated evidence.
