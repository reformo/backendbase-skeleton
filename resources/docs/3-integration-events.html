Integration Events

Define stable event contracts, store them with domain changes, publish them through the outbox, and map versioned messages into idempotent subscribers.

Overview

An integration event is a versioned fact that another component or service can consume. The producer records the fact in the same transaction as its domain change.

Stable contract

The event name, version, and payload shape are compatibility contracts.

Atomic record

The domain mutation and outbox insert commit or roll back together.

Idempotent intake

The inbox uses the consumer name and message ID to stop duplicate database work.

Primary rule Publish business-relevant external effects through the outbox. Do not publish directly from a command handler.

Event types

Backendbase uses separate contracts for domain, producer, and consumer concerns.

TypePurposeExecutionCore contract
Domain event Reports a fact inside one bounded context. Synchronous through DomainEventPublisher. DomainEvent
Producer integration event Defines the published event name, version, time, and payload. Stored by IntegrationEventTransaction. IntegrationEvent
Internal integration subscriber Handles an IntegrationEvent in the current process. Only an explicit EventManager::dispatchEvent() call invokes it. IntegrationEventSubscriber
External integration subscriber Handles a mapped message received from a queue. Asynchronous through the queue processor and inbox. ExternalIntegrationEventSubscriber
Event message Defines the typed payload available to a consumer. Created by Valinor after version lookup. EventMessage
Internal subscribers are not part of the outbox consumer path The queue processor dispatches only ExternalIntegrationEventSubscriber implementations. Project rules also prohibit direct dispatchEvent() calls from command handlers.

End-to-end lifecycle

The event moves through a producer contract, durable storage, transport, version mapping, and a subscriber.

Reference contract

final class ExampleChanged implements IntegrationEvent
{
    public const string EVENT_VERSION = '1.0';
    public const bool IS_MESSAGING_EVENT = true;
    public const string EVENT_TYPE = 'Example_ExampleChanged';

    use IntegrationEventTrait;

    public function __construct(private readonly ExampleChangedPayload $payload)
    {
        $this->occurredOn = DateTimeImmutable::create();
    }

    public function eventName(): string
    {
        return self::EVENT_TYPE;
    }

    public function eventVersion(): string
    {
        return self::EVENT_VERSION;
    }

    public function getEventArguments(): array
    {
        return $this->payload->toArray();
    }
}
The external flag is a convention, not a transaction guard DoctrineIntegrationEventTransaction stores every event returned from the execute() callback. It does not call isExternal() before insertion.

Naming rules

Names must identify the producer service and the business fact.

Producer event type

{PascalCaseServiceName}_{PascalCaseEventClassName}

The service name comes from service-name in config/autoload/global.php.

Consumer event name

{producer EVENT_TYPE}_Event

The queue processor appends _Event before registry lookup and dispatch.

# Default service-name: example
Event class:    ExampleChanged
Producer type:  Example_ExampleChanged
Consumer name:  Example_ExampleChanged_Event
Do not rename a published event Existing names are compatibility contracts. Use a migration plan when a published name must change.

The repository uses the current Example_* names for the example service. Keep published names unchanged unless a planned migration replaces them.

Producer pattern

Create the complete payload after authoritative database work. Keep broker calls outside the command handler.

$this->integrationEventTransaction->execute(
    function () use ($command): ExampleChanged {
        $example = $this->exampleRepository
            ->getActiveByIdentity($command->identity());
        $example->change(
            $command->isActive(),
            $command->value(),
            $command->details(),
        );
        $this->exampleRepository->save($example);

        return new ExampleChanged(new ExampleChangedPayload(
            exampleId: $example->id(),
            isActive: $command->isActive(),
            value: $command->value(),
            details: $command->details(),
        ));
    },
);

Transaction behavior

  1. Start one Doctrine transaction.
  2. Run the database mutation callback.
  3. Serialize getEventArguments() as JSON.
  4. Insert a UUID version 7 outbox row.
  5. Commit both writes or roll back both writes.

Allowed in the callback

  • Aggregate changes
  • Repository writes
  • Synchronous domain listeners that must control rollback

Not allowed in the callback

  • Network calls
  • Process execution
  • Filesystem input or output
  • Direct queue publication

Payloads and versions

The producer payload and consumer message carrier are separate classes. Their serialized shapes must still match for a given event version.

ContractLocationPurpose
Producer payload Contracts/IntegrationEvents/V1 Creates the exact JSON object stored in the outbox.
Consumer message Contracts/ExternalIntegrationEvents/V1 Defines constructor fields and types accepted by the consumer.

Version rules

  • Keep the event name stable when the business fact stays the same.
  • Do not change a released version-one payload shape in place.
  • Create a new versioned payload and consumer carrier for an incompatible change.
  • Change EVENT_VERSION only when the matching consumer registration exists.
  • Keep old message contracts while old messages can remain in queues or outbox tables.
  • Use explicit typed fields. Do not serialize command objects or aggregates directly.
Registry identity The external registry key is eventName:eventVersion. A duplicate key fails container creation. An unknown version fails message processing.

External consumer flow

The queue processor treats contract and mapping errors as permanent failures.

  1. Validate the event type, message ID, consumer name, and event version.
  2. Append _Event to the producer event type.
  3. Claim the inbox key made from consumer name and message ID.
  4. Find subscribers for the derived event name.
  5. Require every matched subscriber to implement the external subscriber interface.
  6. Resolve the message class by event name and version.
  7. Map the payload into the message class with Valinor.
  8. Dispatch the message and commit processed_at.
  9. Acknowledge the queue message.
ResultExamplesQueue outcome
SuccessSubscriber completes, or inbox key is a processed duplicate.ACKNOWLEDGE
Permanent failureMissing metadata, unknown version, no subscriber, wrong subscriber type, or mapping error.REJECT
Transient failureSubscriber or infrastructure throws another exception.RETRY until attempt 5
Database subscriber idempotency InboxMessageTransaction wraps the inbox insert, subscriber work, and processed timestamp in one transaction. A failed database mutation rolls back the inbox insert so the broker can retry.

final readonly class NewExampleAddedExternalSubscriber
    implements ExternalIntegrationEventSubscriber
{
    public const string EVENT_TYPE = 'Example_NewExampleAdded_Event';

    public function __construct(private LoggerInterface $logger)
    {
    }

    /** @param NewExampleAddedMessage $message */
    public function handle(EventMessage $message): void
    {
        $this->logger->debug('NewExampleAdded', $message->toArray());
    }

    public static function getSubscribedEvents(): array
    {
        return [self::EVENT_TYPE];
    }
}

Exact and wildcard names

The event manager supports exact names and fnmatch wildcard patterns such as Partner_*_Event. It hashes subscriber class names so the same subscriber runs once when exact and wildcard entries both match.

Keep subscriber types separate If an internal subscriber wildcard matches an external event name, the external dispatcher rejects the message. It requires all matched subscribers to implement ExternalIntegrationEventSubscriber.

Service provider registration

Register both subscriber kinds in the bounded-context ServiceProvider.

Internal registration

[
    'events' => NewExampleAddedSubscriber::getSubscribedEvents(),
    'subscriberFQCN' => NewExampleAddedSubscriber::class,
]

External registration

[
    'events' => NewExampleAddedExternalSubscriber::getSubscribedEvents(),
    'subscriberFQCN' => NewExampleAddedExternalSubscriber::class,
    'messageFQCN' => NewExampleAddedMessage::class,
    'eventVersion' => NewExampleAdded::EVENT_VERSION,
]

Container startup

  1. The container scans src/Backendbase/Domain/*/ServiceProvider.php.
  2. It adds every subscriber entry to EventManager.
  3. It adds entries with messageFQCN and eventVersion to the external registry.
  4. The registry checks that each message class implements EventMessage.
  5. The registry rejects duplicate event-name and version keys.
Run from the project root The service provider scan uses a relative path. Console and application entry points already change to the project root.

Implementation checklist

Complete every applicable item before release.

  1. Read the configured service name.
  2. Choose a stable producer event type.
  3. Create a versioned producer payload with explicit fields.
  4. Implement IntegrationEvent and use IntegrationEventTrait.
  5. Set EVENT_TYPE, EVENT_VERSION, and IS_MESSAGING_EVENT.
  6. Write the mutation through IntegrationEventTransaction::execute().
  7. Create a matching versioned external message carrier.
  8. Create the external subscriber with the _Event name.
  9. Register subscriber, carrier, and version in ServiceProvider.
  10. Test the exact producer payload against the registered carrier.
  11. Test success, duplicate, invalid, and transient failure paths.
  12. Apply outbox and inbox migrations before deployment.
  13. Run the relay and consumer under operational supervision.
