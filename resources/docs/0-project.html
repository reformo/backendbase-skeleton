01 · Overview

A modular backend service foundation

Backendbase Core is a PHP API project for backend services. It combines Domain-Driven Design, Ports and Adapters, and Command Query Responsibility Segregation.

The current repository provides one consumer API named ExampleApi. It also provides a complete reference bounded context, shared runtime services, persistence adapters, queue adapters, console operations, and API contract tools.

Use this page first. Follow its links when you need the complete rules for one architecture topic.

05 · Architecture

Dependencies point toward contracts and domain rules

The architecture suite enforces Domain and Application direction, bounded-context isolation, both adapter directions, Shared core framework isolation, annotated target integrity, and the rule that Shared must not depend on Application, Domain, or Infrastructure.

06 · Layer boundaries

Keep each concern in its owning layer

LayerOwnsMust avoid
DomainAggregates, invariants, value objects, domain eventsSlim, PSR-7, Doctrine records, queue clients
ApplicationCommands, queries, handlers, orchestration, subscribersHTTP parsing and direct concrete infrastructure calls
ContractsPorts, command and query inputs, read models, event contractsAdapter implementation details
InfrastructureControllers, database adapters, queue adapters, external servicesBusiness rules that belong to aggregates
SharedStable framework-independent building blocksDependencies on application modules
Database boundary: Create only database structures that the requested feature needs. Review every generated migration before execution.

07 · Active modules

The Example bounded context is the reference

ExampleBoundedContext

Contains domain objects, commands, queries, read models, handlers, Doctrine and memory repositories, events, subscribers, a service provider, and module-local tests.

IdentityAndAccess

Provides account registration, revision, retirement, listing, database-backed authentication, JWT access control, HTTP authorization middleware, and authorization exceptions.

ExampleApi

Provides the current HTTP adapter. It contains root controllers, Account and Example controller modules, middleware, and routes.

Service providers

Each bounded context maps ports to adapters and registers integration event subscribers.

Do not assume that another consumer API exists. Scaffold it before adding its controllers, configuration, OpenAPI source, or Bruno collection.

08 · HTTP runtime

A request passes through bootstrap, middleware, and a use case

  1. Front controllerselects ExampleApi
  2. Configurationmerges shared + API files
  3. Containerbuilds dependencies
  4. Middlewareadds request context
  5. Controllercreates command or query
  6. Responseemits PSR-7 output

Entry points

public/index.php can select an API through X-Source-Id. public/example-api/index.php selects ExampleApi directly.

Routes

The root routes provide API metadata, liveness, readiness, and authentication. ModuleRoutes registers the protected Account and Example modules. A final route handles missing paths.

Current security state: ExampleApi middleware validates Backendbase-Api-Key. Protected module routes also validate bearer authorization. Missing or invalid credentials return status 401.

09 · Feature flow

Use contracts to connect adapters to behavior

  1. Define or change the public OpenAPI operation.
  2. Add the bounded context when the business capability does not exist.
  3. Create a command or query contract with its handler attribute.
  4. Implement domain behavior, value objects, and invariants.
  5. Add repository ports and the required persistence adapter.
  6. Implement the application handler and event behavior.
  7. Add focused domain, repository, handler, and lifecycle tests.
  8. Add migrations only when the approved feature changes the schema.
  9. Add the affected API controller, route, OpenAPI source, and Bruno request.
  10. Run generation, validation, static checks, and focused runtime tests.
Write path: The handler tells an aggregate to perform behavior, and then saves it through a write port.
Read path: Use a read adapter with Doctrine DBAL and explicit SQL for projections. Keep SQL out of controllers and domain objects.

10 · Persistence

Doctrine adapters keep storage outside the domain

Write side

Write repositories load and save aggregates. Doctrine records map aggregate state to columns.

Read side

Read repositories return stable read models. DBAL projections can use purpose-built SQL.

Test side

Memory adapters support fast lifecycle tests. Doctrine tests use production metadata and SchemaTool.

The current migrations create and evolve example_table, the integration event outbox, the inbox, and the delivery failure log.

bin/doctrine migrations:diff
bin/doctrine migrations:migrate
Run the migration difference after repository behavior is final. Review all SQL before migration execution.

11 · Messaging

Business writes and event records share one transaction

  1. Commandrequests a state change
  2. Aggregateenforces rules
  3. Transactionsaves state + outbox
  4. Relaypublishes pending events
  5. QueueRabbitMQ or SQS
  6. Subscriberhandles message safely
  • Use IntegrationEventTransaction::execute() for a write and its outbox message.
  • Use synchronous domain listeners only when failure must roll back the command.
  • Use the outbox for business-relevant external effects.
  • Register internal and external subscribers in the bounded context service provider.
  • Keep event names and event versions stable after publication.

RabbitMQ is the default queue driver. Set BACKENDBASE_QUEUE_DRIVER=sqs to select Amazon SQS.

12 · Configuration

Environment values feed layered PHP configuration

Shared configuration

config/autoload/* defines global, logger, Redis, RabbitMQ, AWS, and object-store settings.

API configuration

config/example-api/* defines the API version, key, headers, JWT, base path, and route cache.

The bootstrap loads .env when the compiled configuration cache does not exist. It merges shared providers with the selected API providers.

Typed settings objects validate application runtime, database, queue, AWS, Redis, logging, HTTP, and JWT values. Adapters receive immutable leaf settings instead of configuration arrays.

Secret rule: Keep real keys, tokens, passwords, and service credentials out of version control. Use .env.example only as a variable contract.

See the environment guide for precedence, cache behavior, queue selection, AWS validation, and common failure modes.

13 · Local setup

Start dependencies, migrate, and run the API

  1. Install PHP 8.5, Composer, Docker, and the required PHP extensions.
  2. Install locked Composer dependencies.
  3. Create .env from .env.example. Set local values.
  4. Start MySQL, Redis Stack, and RabbitMQ. Enable the integration profile only when tests need AWS endpoints.
  5. Apply Doctrine migrations.
  6. Generate the merged Example API OpenAPI file.
  7. Start the PHP development server.
  8. Run focused tests and contract checks.
composer install
cp .env.example .env
docker compose up -d
docker compose --profile integration up -d
bin/doctrine migrations:migrate --no-interaction
composer run generate-example-api-spec
composer run start-apis

17 · Deployment

Deployment activates a verified immutable release

  1. Revisionselect exact commit
  2. Artifactinstall production dependencies
  3. Contractgenerate and validate OpenAPI
  4. Preflightverify checksum and migration plan
  5. Activatemigrate and switch link
  6. Verifyreadiness, workers, and logs

build-release.sh verifies reviewed Composer package contents before dependency code executes. It creates an exact commit archive with a CycloneDX SBOM, package-content manifest, and SHA-256 checksum. Stage and production wrappers verify this evidence before migration and activation.

Recovery note: Application rollback can select only the recorded previous release. The expanded database schema remains in place.
