Safe retries with idempotency

A lost response must not turn one intended operation into two. This guide explains how the API remembers an operation and returns its result again.

01 · For every reader

One intended operation has one key

Applications use an application programming interface (API) to request work from the server.

Idempotency means that a retry can return the original result without performing the operation again. The client supplies an Idempotency-Key to identify that intended operation.

For example, registration can succeed while the response is lost. A retry with the same key and request returns the stored registration result.

A timeout does not prove failure. The operation can already have changed data or sent a message. Keep the original key while checking the outcome.

02 · Everyday examples

Keep the operation identity when the connection fails

A registration response is lost

The server creates the Account and stores the response. The application retries the same request with the same key.

Result: The API returns the original result. It does not create another Account.

A contact request is repeated

The first request sends a verification message. A matching retry receives the stored response.

Result: The retry does not send another message. An explicit resend is a new operation with a new key.

Tracing identifies each attempt

X-Request-Id identifies one HTTP attempt for diagnostics. Idempotency-Key identifies the intended operation across attempts.

The trace labels above explain the distinction. Use valid universally unique identifiers (UUIDs) for actual trace headers.

Client responsibility: Two clicks with two new keys are two operations. The client must retain one key for duplicate submissions of the same intended action.

03 · Response decisions

Use the response to select the next action

Response or conditionMeaningNext action

Missing-key, authentication, and body-size rejection happen before the claim. These rejections are not stored.

04 · For developers

Keep the request unchanged during a retry

Every current POST, PATCH, and DELETE operation requires the header. The middleware also supports PUT on a named write route. GET, HEAD, and OPTIONS need no key.

  1. Generate an unpredictable key when the user starts an intended operation. A UUID is suitable.
  2. Retain the key and the exact request while the outcome is unknown.
  3. Reuse that key for retries of the operation.
  4. Generate a new key for a separate intended operation or a corrected payload after checking the earlier outcome.

Header format

Send exactly one unquoted value containing 1 to 255 characters. Start with an ASCII letter or digit. Remaining characters can also include ., _, :, and -.

Idempotency-Key: 019f6322-1234-7000-8000-000000000001
X-Request-Id: 019f6322-1234-7000-8000-000000000002
Developer details: request matching and scope

The stored key scope contains the operation ID, caller identity, and key. Authenticated identity includes realm, Account, and actor. Public authentication uses an anonymous scope for its operation.

Operation IDs separate the inbound APIs. Keep them stable while retained claims exist.

A request fingerprint is a derived value used to compare request content. Its calculation uses a secret key.

The request fingerprint includes the method, path, raw query string, exact body bytes, and these headers:

  • Content-Type, Accept, and Accept-Language.
  • The-Timezone-IANA, Authorization, and Backendbase-Api-Key.

JSON whitespace and query ordering matter. Changing credentials also changes the fingerprint. X-Request-Id can change between attempts.

The fingerprint is keyed. An anonymous key cannot replay a different caller's request content without matching its credentials and payload.

Developer details: response contract and Bruno requests

Replay preserves the original status and body. Selected headers are Content-Type, Cache-Control, Content-Language, Backendbase-Insert-Id, Location, and Retry-After.

Trace, cookie, transport, and cross-origin headers are not stored for replay.

The raw request-body limit is 65,536 bytes. Stored response bodies must fit within 1 MiB. Oversized responses leave their claims unresolved and return 503.

Maintained Bruno writes use {{$randomUUID}}, which creates a new key for each send. Replace it with one fixed test key when checking retries.

05 · Mechanism

The server records a claim before doing the work

  1. ValidateCheck required headers and applicable authentication.
  2. ClaimCommit a unique request claim in MySQL.
  3. ExecuteRun the existing application operation.
  4. RememberEncrypt and commit the response, then return it.
Stored stateMatching retryRetention
No claimOne caller can claim and execute.Not applicable.
Claim without a stored responseReturn 409. No caller can take over automatically.No automatic expiry.
Completed claimReturn the stored result without execution.24 hours after completion. Reads do not renew it.
Expired completed claimThe key can start another operation.The expired record can be removed.

The MySQL primary key prevents two accepted claims for the same scoped key. All API instances must use the same replay database and encryption secret.

The work and response are separate commits. A crash after a change but before response storage leaves an unresolved claim. The server blocks another execution under that key.
Developer details: storage and application boundaries

http_request_replay stores request and content digests, encrypted responses, and timestamps. Raw keys, request bodies, passwords, and credentials are not stored there.

Sodium authenticated encryption protects responses, including login tokens and personal data. The cipher binds each response to its request identity.

The replay store commits independently. HTTP middleware does not open an outer transaction around business handlers.

Existing application transactions, Redis changes, and notification delivery keep their current boundaries. MySQL and an external provider do not share one transaction.

The request primary key supports claim, lookup, completion, and single-key expiry checks. http_request_replay_expiry_idx supports ordered cleanup.

2. The inbound API selects and authenticates the request

  1. Bootstrap: A proposed selector entry maps X-Source-Id: payments to the payment API. Bootstrap validates trace and timezone input.
  2. Routing: The API's module registry resolves POST /payments to a named operation and handler. Its operation ID stays stable.
  3. Authentication: API-key validation and the fixed USER realm policy precede bearer authentication. Current identity and session checks must pass before replay.
  4. Replay input: Shared middleware validates the idempotency header and bounded request body. Authentication and input rejection at this stage create no replay claim.

A browser preflight checks the configured cross-origin policy. OPTIONS does not claim a payment or invoke its business handler.

3. The middleware commits the HTTP claim

The scope combines the named operation, USER realm, Account, actor, and client key. The fingerprint includes the request content and relevant headers.

A unique MySQL claim lets one request proceed. A matching completed claim returns its stored response before the payment handler runs.

A concurrent or unresolved matching request receives 409. Changed content under the same scoped key receives 422. Neither branch calls the provider.

PHP: claim, replay, execute, and store

This method is copied from the existing Idempotency middleware. Reuse that middleware for the proposed route.

private function processWrite(ServerRequestInterface $request, RequestHandlerInterface $handler, string $key): ResponseInterface
{
    $exchange = $this->exchange;
    $store    = $this->store;
    $identity = $exchange->identity($request, $key);
    $stored   = $store->claim($identity);
    if ($stored !== null) {
        return $exchange->replay($identity, $stored);
    }

    $response  = $exchange->execute($request, $handler);
    $encrypted = $exchange->encrypt($identity, $response);
    $store->complete($identity, $encrypted);

    return $response;
}

claim() returns null only for a new committed claim. It returns ciphertext for a completed matching claim.

The store throws RequestMismatch or RequestOutstanding for conflicting claims. The enclosing process() maps these exceptions to 422 or 409.

execute() translates application exceptions into safe HTTP responses. Those error responses are encrypted and stored too.

A storage failure returns 503. A claim without a stored response remains blocked. The middleware does not delete it after an exception.

4. The application prepares a durable payment attempt

  1. HTTP handler: Validate the JSON fields and construct typed application input. Invoke one application operation.
  2. Business authorization: Verify that the caller can pay this order. Validate the payment-method token through the provider boundary as required.
  3. First business transaction: Lock the order and check its authoritative amount, currency, and payment state.
  4. Duplicate protection: Enforce one active or successful attempt per order with a database constraint and transactional checks.
  5. Commit before charging: Save a pending payment, its payment identifier, and a stable provider-operation key. Commit this transaction before calling the provider.

A different HTTP key can reach this business check. It must not create another charge for an order that already has an active or successful payment.

5. The provider charges and the application records the result

  1. Provider adapter: Send the stored amount, currency, token, and provider-operation key with an explicit timeout.
  2. Provider retries: Reuse the same provider key and charge parameters within the provider's documented guarantees. Use bounded retries only for transient failures.
  3. Validate the result: Check the provider response, payment reference, amount, currency, and status before accepting success.
  4. Second business transaction: Lock the payment and order. Record the successful charge and mark the order paid.
  5. Receipt event: Write the receipt event to the transactional outbox in the same transaction. Commit payment state and the event together.

The outbox relay can publish more than once. The receipt consumer needs its own durable duplicate protection for delivery.

A receipt failure does not repeat the charge. Its delivery retry belongs to the notification flow.

PHP: commit the attempt, call the provider, then commit the outcome

The proposed PayOrderHandler belongs in the payment context's Application/CommandHandlers directory. Its command handler returns void.

use Backendbase\Shared\CQRS\Command;
use Backendbase\Shared\CQRS\CommandHandler;

final readonly class PayOrderHandler implements CommandHandler
{
    public function __construct(
        private PaymentAttemptWrites $attempts,
        private PaymentProvider $provider,
    ) {
    }

    /** @param PayOrder $command */
    public function handle(Command $command): void
    {
        $access = $command->accessControl();
        if (! $access->isAllowed('payment.create')) {
            throw new PaymentNotAllowed();
        }

        $attempts = $this->attempts;
        $provider = $this->provider;
        $attempt  = $attempts->prepare($command);
        $charge   = $attempt->chargeRequest();

        try {
            $outcome = $provider->charge($charge);
        } catch (ProviderOutcomeUnknown $exception) {
            throw new PaymentOutcomeUnknown(
                'Check the existing payment before another attempt.',
                0,
                $exception,
            );
        }

        $paymentId = $command->paymentId();
        $attempts->complete($paymentId, $outcome);
        $outcome->assertSucceeded();
    }
}

PaymentProvider is a context-owned port. Its infrastructure adapter sets finite connection and request timeouts and validates every provider response.

chargeRequest() contains the stored provider-operation key, amount, currency, and payment-method token. It never derives a provider key from an HTTP retry.

A timeout or an ambiguous response raises ProviderOutcomeUnknown. The attempt remains pending. The handler does not repeat the charge.

A confirmed decline is persisted before assertSucceeded() raises the documented business problem. Only a confirmed terminal outcome can release the order's active-attempt guard.

The two business transactions

The proposed application service below uses context-owned persistence ports. PaymentTransaction::run() commits before returning and rolls back when its callback throws.

final readonly class PaymentAttemptWrites
{
    public function __construct(
        private PaymentWriteRepository $repository,
        private PaymentTransaction $transaction,
    ) {
    }

    public function prepare(PayOrder $command): PaymentAttempt
    {
        $transaction = $this->transaction;
        $work = fn (): PaymentAttempt => $this->reserve($command);

        return $transaction->run($work);
    }

    private function reserve(PayOrder $command): PaymentAttempt
    {
        $repository = $this->repository;
        $orderId    = $command->orderId();
        $order      = $repository->getOrderForUpdate($orderId);
        $access     = $command->accessControl();
        $order->assertPaymentAllowed($access);

        $paymentId   = $command->paymentId();
        $providerKey = ProviderOperationKey::forPayment($paymentId);
        $methodToken = $command->paymentMethodToken();
        $attempt     = $order->startPayment($paymentId, $providerKey, $methodToken);
        $repository->savePending($order, $attempt);

        return $attempt;
    }

    public function complete(PaymentId $paymentId, ChargeOutcome $outcome): void
    {
        $transaction = $this->transaction;
        $work = fn () => $this->record($paymentId, $outcome);
        $transaction->run($work);
    }

    private function record(PaymentId $paymentId, ChargeOutcome $outcome): void
    {
        $repository = $this->repository;
        $order      = $repository->getOrderForPaymentUpdate($paymentId);
        $receipt    = $order->recordPaymentOutcome($paymentId, $outcome);
        $repository->saveOutcomeAndOutbox($order, $receipt);
    }
}

startPayment() rejects an active attempt or a paid order and uses the order's authoritative price. savePending() persists the attempt and order guard together.

The proposed schema needs a unique guard per order. Every payment write must lock the same order before its payment record.

recordPaymentOutcome() checks the payment identity, provider reference, amount, currency, and permitted state transition before mutation.

Repeated matching outcomes produce no new receipt event. Conflicting terminal outcomes fail explicitly. saveOutcomeAndOutbox() writes the order, payment, and optional receipt event in one transaction.

The receipt event uses a stable identity derived from the payment identifier. A unique outbox identity prevents duplicate receipt creation during recovery.

The ports hide SQL and Doctrine details. The proposed tables, constraints, indexes, and provider-token retention require their own design and verification.

6. The API stores the response before returning it

The application returns a declared result after the business commit. The HTTP handler maps that result to a hypothetical 201 response:

{"payment":{"id":"019f6322-1234-7000-8000-000000000104","status":"succeeded","amountMinor":25900,"currency":"TRY"}}

amountMinor expresses the amount in the currency's smallest unit. Here, 25,900 kuruş equals TRY 259.00.

The middleware encrypts the status, body, and selected response headers. It completes the replay claim in a separate commit, then returns the response.

The HTTP claim, pending-payment record, successful-payment record, and stored HTTP response are separate commits. The provider charge occurs between the business transactions.

PHP: read the committed result and map the HTTP response

The proposed PayOrderAndRead application orchestrator dispatches one command and then reads the committed payment.

use Backendbase\Shared\CQRS\CommandBus;
use Backendbase\Shared\CQRS\QueryBus;

final readonly class PayOrderAndRead
{
    public function __construct(private CommandBus $commands, private QueryBus $queries)
    {
    }

    public function pay(PayOrder $command): PaymentView
    {
        $commands = $this->commands;
        $commands->handle($command);

        $paymentId = $command->paymentId();
        $access    = $command->accessControl();
        $query     = new GetPayment($paymentId, $access);
        $queries   = $this->queries;

        return $queries->handle($query);
    }
}

PayOrder and GetPayment belong in the payment context's Contracts layer. Register both handlers in its ServiceProvider::getHandlers() map.

The query repeats access checks and reads the primary database. A missing result or read failure raises a safe error without repeating the command.

PHP: reconcile the existing attempt after a provider timeout

A proposed recovery command handler can call this application function with context-owned ports. The function returns no command result.

function reconcilePayment(
    ReconcilePayment $command,
    PaymentRecoveryRead $recovery,
    PaymentProvider $provider,
    PaymentAttemptWrites $attempts,
): void
{
    $attempt  = $recovery->getAuthorizedAttempt($command);
    $lookup   = $attempt->statusRequest();
    $outcome  = $provider->status($lookup);

    $paymentId = $command->paymentId();
    $attempts->complete($paymentId, $outcome);
}

getAuthorizedAttempt() enforces recovery authority and reads the stored provider identity. It leaves no transaction open during status lookup.

status() returns only a validated terminal outcome. A pending, missing, malformed, or unavailable provider result raises ProviderOutcomeUnknown.

That exception leaves the existing attempt pending. A lookup failure does not authorize another charge. Completion uses the same transaction and receipt identity as normal execution.

This command does not complete, delete, or replace the HTTP replay claim. A stored HTTP error still replays unchanged after business recovery.

Do not clear evidence to retry a charge. Keep unresolved HTTP claims and payment attempts while checking the provider. Backendbase has no automatic claim takeover or payment-recovery command. Any payment recovery described here would require a dedicated, authorized implementation.

HTTP encryption and cleanup follow the existing contract. Payment records and provider evidence need their own retention policy.

Logs can connect the trace, payment identifier, and safe provider reference. They must exclude credentials, payment-method tokens, and card data.

07 · Authentication and contact flows

Replay preserves results and current access checks

  • Login: A matching retry returns the original token. It does not issue another session, renew token expiry, or restore a revoked session. A fresh login needs a new key.
  • Protected writes: API-key and bearer checks run before replay where required.
  • Logout, token revocation, and Account closure: A successful action can make its own retry credentials invalid. The retry then returns 401.
  • Contact request, confirmation, and resend: Matching retries do not send another message, consume proof again, or extend verification time.
  • Explicit resend: Use the documented resend operation with a new key. Cooldown and quota checks still apply.

A login response can remain replayable after its token expires. An earlier failed login can also remain stored after Admin approval. Start a fresh login with a new key.

Activation sequence

  1. Update clients to send stable operation keys.
  2. Prepare the dedicated secret and review the target database migration.
  3. Apply the migration through the authorized deployment procedure.
  4. Stop writes during mixed-version activation. Older nodes do not enforce this contract.
  5. Activate the new code and clear route caches.
  6. Verify a successful write, matching replay, changed-body rejection, and cleanup on the prepared target.
Key rotation needs a recovery plan. Online replay-key rotation is not implemented. A changed secret invalidates retained fingerprints and ciphertext. Drain writes. Reconcile unresolved claims. Wait for completed replay windows to end before an authorized replacement.

Preserve the secret with encrypted backups. Restore claim evidence consistently with business data. The reverse migration refuses to drop replay evidence.

09 · Operations and support

Remove expired results and preserve uncertain outcomes

Run the cleanup command only on the identified, authorized target:

bin/backendbase idempotency:cleanup

One run removes up to 500 expired completed responses. Repeat bounded runs for the deployment's volume. The application installs no automatic schedule.

Cleanup never removes unresolved claims. Access to an expired completed key can also remove that one record before a new claim.

When a 409 remains unresolved

  1. Keep the original operation key and available trace identifiers.
  2. Check whether the original process is still active.
  3. Inspect business records, message evidence, Redis state, and provider evidence for the actual outcome.
  4. Keep the claim blocked while the outcome is uncertain.
  5. Use a separately authorized recovery procedure after proving the outcome.

No automatic claim takeover or operator reconciliation command is provided. Do not delete a claim, reset its timestamps, or generate a new key merely to bypass an unresolved result.

Monitor replay-storage failures, persistent outstanding claims, cleanup backlog, and database growth. Keep credentials, tokens, verification codes, and request payloads out of diagnostic logs.

10 · Important limits

Know what duplicate protection guarantees

  • The key must be reused. Different keys do not share duplicate protection.
  • Completed retention is finite. After 24 hours, the same key can execute again. Do not automatically retry an uncertain old operation.
  • Unresolved retention is indefinite. Safety requires investigation and can increase storage use.
  • Failures can be replayed. An earlier 400, 429, 500, or 503 returned during execution can remain the stored result.
  • External effects can be uncertain. Provider acceptance does not prove delivery. Replay does not establish exactly-once external delivery.
  • Recovery evidence matters. Losing claims or restoring older claims can permit duplicate execution.
