01 · Verdict

Code quality is strong. One sample boundary blocks production readiness.

Code quality and maintainability score: 9.4 out of 10. Static analysis and coding standards now cover operational PHP and database delivery code. CI actions use immutable commit SHAs, and Composer uses an exact secure version. Complexity, documentation, report, and supply-chain checks now have executable gates.
Production-readiness exception: POST /auth issues a token after input validation, but it does not verify the supplied credentials.

Architecture rules, failure paths, API contracts, health behavior, and deployment behavior have strong automated verification.

Recent changes added typed settings, strict numeric parsing, observable queue failures, a lazy Redis connection, and an opt-in local AWS emulator. A weekly audit, CycloneDX SBOM, and reviewed package-content digests now protect Composer changes.

The code-quality score excludes product readiness. The sample authentication route remains the first remediation priority. Other findings concern repeatability, dependency cost, and external deployment ownership.

The architecture does not need a broad rewrite. Apply focused fixes with regression tests.

04 · Strengths and outcomes

The project connects design rules to operational outcomes

Architecture boundaries

Architecture tests enforce domain purity, adapter direction, bounded-context isolation, framework boundaries, and Shared-layer direction.

Failure-path testing

Tests cover invalid input, rollback, retry exhaustion, duplicate messages, malformed data, and deployment recovery.

Static guardrails

PHPStan level 8, the Doctrine coding standard, and a complexity limit of 15 cover production, tests, tools, and database delivery code.

Strong automated gates

Continuous integration runs tests with a 100% line gate, static analysis, complexity, coding standards, isolated dependency verification, security checks, and OpenAPI validation.

Typed configuration boundaries

Focused objects validate runtime values. Adapters receive immutable settings. Redis opens its socket only when the first command runs.

Reliable integration design

Inbox, outbox, retry, external-effect, and dead-letter behavior is explicit and well tested.

Health and local infrastructure

Liveness stays cheap. Readiness uses bounded checks. Digest-pinned local services include an opt-in Moto profile for S3, SQS, and SNS.

API contract coverage

OpenAPI sources, generated output, controller tests, Bruno requests, and an authenticated ZAP workflow cover the example API contract.

Defensive delivery controls

Release scripts verify manifests and checksums. Weekly audits and isolated installs verify the SBOM and 134 package-content digests.

Change risk is visible early.
Architecture, type, behavior, and contract drift become repeatable failures.
Message delivery favors consistency.
Outbox, inbox, retry, and external-effect claims have explicit failure behavior.
Operations have stop conditions.
Readiness, backup hooks, manifests, activation checks, and rollback checks define failure gates.

05 · Risks and weaknesses

One product risk is urgent. The remaining risks need active ownership.

PriorityRiskEffectEvidence
High Sample authentication does not authenticate POST /auth assigns a fixed user identifier and issues a JSON Web Token without verifying either credential. Authenticate.php and the example OpenAPI contract.
Medium Mutable security scanner image The Semgrep container uses a version tag without an image digest. GitHub Action references already use immutable commit SHAs. security-checks.yml.
Medium No local Firebase integration profile Moto provides local S3, SQS, and SNS endpoints. Firebase still requires an external service or a separate emulator. docker-compose.yaml and FirebasePushNotifier.php.
Medium Deployment safety depends on external hooks The flow requires backup and activation hooks. The repository cannot verify each server's backup, PHP reload, or worker restart implementation. deployment guide and deploy-release.sh.
Low Optional integration dependency surface Projects maintain database, queue, cache, notification, cloud, and API packages even when they do not enable every capability. 35 direct and 97 locked runtime packages remain. All are maintained, and 34 direct packages are current.
Low Dependency review still requires human judgment A content digest detects a package change but cannot determine whether the changed code is safe. Reviewers must explain lock, SBOM, and content-digest changes before approval.

06 · Recommended order

Reduce product risk before maintenance cost

Now

Protect trust boundaries

  • Remove, restrict, or implement POST /auth.
  • Add invalid-credential tests.
  • Pin the Semgrep image by digest.
Next

Strengthen repeatability

  • Version and rehearse deployment hook examples.
  • Test Guzzle 8 across Tolgee, AWS, and Firebase.
  • Upgrade both coding tools as one change.
Then

Reduce adoption cost

  • Measure production install size and advisory work.
  • Add local Firebase only when tests justify its maintenance cost.
  • Add signed release provenance when the platform supports verification.
Keep changes focused. The architecture does not need a broad rewrite. Make each improvement through a focused change with a regression test.
