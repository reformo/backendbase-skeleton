01 · Overview

Notification models are independent from providers

Shared notification objects describe a delivery request. The application-facing Notify port accepts one email, push, or SMS notification directly. StackNotifier selects a provider by notification type.

Email

Addresses, sender, subject, HTML, template data, and attachments.

Push

Title, body, topic, device token, image, and string-compatible data.

SMS

E.164 phone number and non-empty message.

04 · Provider stack

Select providers by stable type names

Providers implement NotificationProvider and return NotificationResult. StackNotifier stores one provider per type. It accepts a direct notification or a StackNotification. A batch checks all provider types before sending. Repeated types keep each message ID in delivery order through messageIds().

A missing provider raises UnexpectedValueException. A provider failure during a batch raises NotificationBatchFailed with completed deliveries and the failed item index. Check external outcomes before retrying a partial batch.

05 · SMS providers

Select SNS, Twilio, or Netgsm

All three adapters accept SmsNotification. SNS is the default. Set BACKENDBASE_SMS_DRIVER=twilio or netgsm to select one provider. Only the selected adapter is registered for the sms type.

  • SnsNotifier uses the AWS SMS type and optional sender ID.
  • TwilioSmsNotifier uses a Twilio account SID, auth token, and sender. It returns a message SID.
  • NetgsmSmsNotifier uses API sub-user credentials, a registered sender, and an encoding. It returns a job ID.
  • The model uses E.164 format. Netgsm receives Turkish numbers in national format and other numbers with a 00 prefix.

A message SID or job ID confirms provider acceptance. It does not confirm delivery to the handset. Netgsm defaults to TR encoding. Configure a different encoding when the message content requires it. The adapter omits iysfilter, which Netgsm treats as informational traffic. Commercial messages need a separate content and consent contract.

06 · Push with Firebase

Firebase maps one push model into CloudMessage

FirebasePushNotifier maps typed notification fields into CloudMessage. It sends to one topic or device token. It supports custom data, platform options, and an image from setNotificationImage(). Relative image paths require CDN_BASE_URL. It does not log the payload.

Registration: Set FIREBASE_PROJECT_ID to register push delivery. Set FIREBASE_CREDENTIALS_PATH or provide Google application credentials.

07 · Email providers

SES or SMTP sends rendered HTML email

SesEmailNotifier sends raw MIME through Amazon SES by default. Set BACKENDBASE_EMAIL_DRIVER=smtp to use SmtpEmailNotifier. Both use EmailMessageFactory for recipients, HTML, and attachments. SMTP supports smtps, required starttls, or explicit none encryption.

The SES client disables automatic retries for email sends. A connection failure can leave the send outcome unknown. Check that outcome before sending the email again.

Template metadata: The email providers do not render a template. Supply the rendered HTML body before delivery.

09 · Idempotency

External delivery needs explicit outcome state

ExternalEffectInbox::processOnce() prevents concurrent or repeated provider calls. It distinguishes success, in-progress work, and unknown external outcome.

A provider can accept a request before the process records success. Treat an unknown outcome as a manual or permanent-failure case, not an automatic duplicate send.

11 · Current gaps

Known notification limits

  • No notification queue producer or consumer contract exists.
  • Push delivery requires Firebase project configuration and credentials.
  • SES requires a verified sender identity in the target account.
  • SMTP provides no provider message ID through the mailer interface.
  • Grouped delivery can have a partial external outcome; callers must inspect NotificationBatchFailed.

13 · Checklist

Add a notification type safely

  • The model validates required external data.
  • The provider has one stable type name.
  • The container registers the provider.
  • Secrets stay in configuration.
  • The queue model maps without data loss.
  • Idempotency and unknown outcomes are handled.
  • Logs exclude sensitive content.
  • Failure-policy tests pass.
