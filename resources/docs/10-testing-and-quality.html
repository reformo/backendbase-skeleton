03 · Test layers

Each layer proves a different contract

  1. Value objectinvariants and boundaries
  2. Aggregatebusiness state changes
  3. Handleruse-case orchestration
  4. Repositorymapping and SQL
  5. APIHTTP translation
  6. E2Erunning system evidence

Do not replace a narrow unit test with a slow end-to-end test. Do not claim runtime behavior from static analysis alone.

04 · Fast tests

Keep domain and application feedback deterministic

  • Test value-object invalid, boundary, and valid inputs.
  • Test aggregate invariants before repository behavior.
  • Use memory repositories for complete in-process lifecycles.
  • Stub ports at application boundaries.
  • Assert emitted events when the event is part of the use-case contract.
  • Do not make live network calls.

05 · Database tests

Use real mapping metadata and isolated schemas

Doctrine repository tests use production mapping metadata. They verify state mapping, SQL filters, ordering, pagination, null behavior, JSON data, enums, and rollback.

Do not copy mapped tables into handwritten test DDL. Use Doctrine SchemaTool with the production record metadata.

06 · API and contract

Verify both adapter behavior and the published contract

  • Controller tests check input parsing, bus dispatch, response status, headers, and body shape.
  • Routing tests check method, path, module registration, and authorization grouping.
  • OpenAPI validation checks document structure.
  • Bruno checks documented Example API operations against a running API and writes an HTML report.
  • OpenAPI and Bruno do not replace failure-path PHPUnit tests.

08 · Coverage

Coverage reports show exercised code, not correctness

composer test writes clover.xml and uses bin/check-coverage.php to require 100% executable-line coverage.

  • Use coverage to find untested branches.
  • Do not use percentage alone as acceptance evidence.
  • Prioritize validation, failure, rollback, retry, and mapping branches.

09 · Verification workflow

Expand checks in proportion to risk

  1. Run the smallest failing or changed test file.
  2. Run the owning directory.
  3. Run related persistence, API, or queue tests.
  4. Validate OpenAPI when the public contract changes.
  5. Run PHPStan at level 8.
  6. Run PHPCS.
  7. Run the full suite for broad changes.
  8. Run Bruno only with a prepared API, credentials, and data.

10 · Automation state

Local and continuous-integration gates use the same commands

GitHub Actions runs Composer validation, dependency audit, PHPUnit with the coverage gate, PHPStan, PHPCS, and OpenAPI validation.

The coverage policy is executable. The normal composer test command rejects any uncovered executable source line.

11 · Current gaps

Known quality-tool differences

  • Rector is not configured or installed.
  • Bruno needs external runtime state and is not a self-contained suite.

composer cs-check

# Contract and E2E
vendor/bin/php-openapi validate public/example-api/docs/example-api-merged.yml
bin/bruno example-api local
# Report: artifacts/bruno/example-api/local.html
