01 · Overview

Translate failures at architectural boundaries

Domain and application code raise typed failures. HTTP adapters translate them into stable public responses. Logs keep the internal diagnostic context.

Expected problem

A pure DomainException becomes application/problem+json at the HTTP boundary.

HTTP or unexpected error

HttpErrorHandler maps Slim exceptions and safe server failures.

PHP shutdown error

ShutdownHandler logs the last PHP error and emits a 500 response.

02 · Failure flow

One of three boundaries owns the response

  1. Operationraises a typed domain error
  2. Slim handlercatches the error
  3. HTTP mapperselects the public contract
  4. Loggerrecords diagnostics
  5. Problem bodykeeps public contract
  6. Emitteradds response headers

03 · Problem Details

Public failures use a stable five-field core

{
  "type": "about:blank",
  "code": "general/resource-not-found",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "The example was not found."
}

ActionError serializes these fields and merges approved context. DomainErrorProblemDetailsMapper provides status, type, code, and title.

04 · Domain errors

The HTTP adapter maps known domain errors

HttpErrorHandler passes each domain error to DomainErrorProblemDetailsMapper. It then translates message keys, replaces :placeholder values, and returns JSON.

Domain and application code do not contain HTTP status, type, code, or title values.

ExampleAlreadyExists maps to status 409 and code example/already-exists. Repository adapters throw the same pure domain error for active identity conflicts.

Only put public and non-sensitive values in additional problem data. The array becomes part of the response.

Unexpected exceptions return a safe 500 message. Only local development aliases and the test mode can add exception details to the response. Stage, CI, production, and unknown modes hide them.

06 · Shutdown errors

Fatal PHP state still gets a structured response

The shutdown handler ignores deprecation errors. It logs other last-error data and passes an internal-server exception to the HTTP error handler.

Stage, CI, and production keep displayErrorDetails disabled. File paths, traces, and exception messages must not appear in shared-environment responses.

07 · Logging

Monolog writes structured context with a stable channel

The configured logger name is backendbase-app. It writes to standard output when the docker environment key exists. Otherwise, it writes to var/logs/app.log.

Unexpected failures log the exception class, message, file, line, and trace. Protect log access and retention because this context can contain internal data.

BACKENDBASE_LOGGER_LEVEL is the primary level input. BACKENDBASE_DEBUG is the fallback.

Use valid Monolog level names. Invalid names fail while configuration is evaluated.

08 · Trace identifiers

Every logger instance receives one trace ID

The container reads X-Request-Id. When it is absent, it creates a UUID version 7. The logger processor writes it as extra.trace_id.

Pass the same request identifier across HTTP calls and queue messages when the contract supports it. Do not generate a new identifier at every internal layer.

10 · Diagnostic safety

Logs can diagnose without exposing secrets

  • Log exception type, stable operation, message identifier, and trace identifier.
  • Do not log access tokens, passwords, API keys, signing keys, AWS secrets, notification content, or unnecessary personal data.
  • Keep stack traces in internal logs.
  • Use stable public error codes for client behavior.
  • Preserve the previous exception when translating a failure.

11 · Current gaps

Known diagnostic limits

  • Authorization middleware uses custom 400 bodies instead of the shared problem flow.
  • TooManyRequests uses status 409 instead of the common 429 status.
  • The logger records full traces for some application problems.
  • No metrics, tracing exporter, dashboard, or alert configuration exists in the repository.
